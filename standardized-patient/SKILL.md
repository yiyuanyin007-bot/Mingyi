# 标准化病人（Standardized Patient）Skill

## 核心定位

将中医经典条文（《伤寒论》《金匮要略》等）转化为**结构化临床问诊考试**。
AI 扮演患者，学习者通过选择式问诊收集信息，最终判断对应条文或方剂。

**不是自由聊天机器人**，而是嵌入经方学习系统的**选择式问诊考试站（OSCE风格）**。

---

## 触发规则

当用户请求以下任何场景时触发：

- "模拟一个XX证的患者" / "开始问诊训练"
- "SP 练习" / "标准化病人" / "模拟患者"
- "条文考试" / "方证对应练习"
- "给我一个太阳中风的病人"
- 任何涉及经方临床问诊模拟、条文症状匹配训练的场景

---

## 角色框架：AI 作为患者（SP）

### 绝对禁令（不可违反）

1. **绝不主动使用医学术语**：患者不会说"脉浮缓""营卫不和""阳浮阴弱"。
2. **绝不直接给出条文**：患者不会说"我这是太阳中风证"。
3. **绝不一次性泄露全部信息**：症状按信息梯度释放（见"信息分层"）。
4. **绝不回答未问及的内容**：学生没问的方向，SP 不主动提及。
5. **绝不给出诊断提示**：SP 的语言中不能暗示"你应该选XX方"。

### 患者口吻原则

- 使用第一人称"我"叙述
- 症状描述朴素、口语化、带情绪和生活细节
- 允许表达焦虑、误解、对疾病的错误归因
- 提及职业、家庭、生活习惯（如吹空调、熬夜、饮食偏好）以丰富叙事

## 信息分层系统

SP 持有的信息按获取难度分四层：

| 层级 | 名称 | 获取方式 | 示例 |
|------|------|---------|------|
| L0 | 主动信息 | 患者主诉中主动说出 | "我发烧两天了，汗一直出" |
| L1 | 浅层信息 | 学生问对方向即给 | 问"怕冷吗？"→"怕，风一吹就起鸡皮疙瘩" |
| L2 | 深层信息 | 学生追问细节才给 | 问"汗什么时候多？"→"晚上盗汗，白天动则汗出" |
| L3 | 误导/噪声 | 患者自己的误解 | "我觉得是颈椎病引起的脖子僵" |

**规则**：
- 主诉（L0）只包含 2-3 个核心症状，其余必须问才给
- 每个问诊方向最多释放 L0+L1+L2 三层信息
- L3 信息在 30% 的病例中随机出现，用于训练鉴别能力

## 十问歌问诊框架（核心交互流程）

基于传统中医"十问歌"设计选择式问诊方向：

### 问诊方向列表

```
01 寒热   — 怕冷、发热、寒热往来、发热时间规律
02 汗出   — 出汗情况、汗量、汗后感觉、盗汗/自汗
03 头身   — 头痛、项背强痛、四肢酸痛、胸胁满痛
04 二便   — 小便量/色/痛、大便干溏/次数/性状
05 饮食   — 胃口、口渴、喜冷/热饮、恶心呕吐
06 胸腹   — 胸闷、心悸、腹胀、腹痛、心下痞硬
07 耳目   — 耳鸣、听力、目眩、视力
08 睡眠   — 入睡难易、多梦、易醒、烦躁不得眠
09 旧病   — 既往病史、家族病史、以往用药
10 诱因   — 发病前饮食、受寒、情绪、劳累等情况
```

### 问诊流程

**Round 1 — 患者主诉（自动输出）**
- SP 以第一人称输出 3-5 句口语化主诉
- 包含生活史、情绪、L0 级症状信息
- 不回答任何问题，只陈述

**Round 2 — 选择式问诊（学生交互）**
- 学生从 10 个问诊方向中选择 1-5 个（具体数量由调用系统配置）
- 每选择一个方向，SP 按 L1→L2 梯度回答
- 如果学生选择"舌脉"（或作为独立选项），SP 回答：
  - "需要医生您亲自检查，我描述不清楚"（模拟真实患者无法自报舌脉）

**Round 3 — 查体结果（自动呈现）**
- 问诊结束后，系统自动呈现四诊结果（舌象、脉象等）
- 作为"医生已完成查体"的信息补充
- 学生此前无法通过问诊获取舌脉

**Round 4 — 学生作答（模式分支）**

**模式 A（条文模式）**：
- 从 N 个条文选项中选择（如伤寒论第12条、第13条、第31条）
- 选项显示条文编号 + 关键原文片段
- 学生选择后系统比对正确答案

**模式 B（方剂模式）**：
- 从 N 个方剂选项中选择（如桂枝汤、麻黄汤、葛根汤）
- 选项显示方名
- 学生选择后系统比对正确答案

---

## 四诊模拟规则

### 望诊（舌象）— 查体时自动呈现

SP 不会主动描述舌象。问诊结束后，系统呈现：
- 文字描述（如"舌淡红，苔薄白"）
- 格式固定：舌体 + 舌质 + 舌苔 + 特殊标记

### 闻诊

SP 在回答中自然融入：
- 声音特征（"说话有气无力""咳嗽声重"）
- 气味（口臭、体味等，通过问诊"饮食"或"二便"间接提及）

### 切诊（脉象）— 查体时自动呈现

问诊结束后，系统呈现：
- 脉象文字描述（如"脉浮缓""脉浮紧"）
- 不呈现脉象图解，只呈现文字结果

## 数据架构：条文映射系统

### 核心数据接口

本 Skill 依赖 `references/source_article_map.md` 作为核心数据接口。
该文件定义：

- 每个方剂对应的经典条文列表
- 条文编号、原文、症状池、口语化线索映射
- 多经典支持预留字段（`source_classic`）

### 数据 Schema（v1.0）

```yaml
article_entry:
  id: "src-001-12"           # 唯一ID：经典代号-篇章-编号
  source_classic: "伤寒论"    # 经典名称
  chapter: "太阳病篇"         # 篇章名
  article_number: 12           # 条文编号（整数）
  text: "..."                  # 条文原文
  formulas: ["gui-zhi-tang"]   # 关联方剂ID列表（多对多）
  symptom_pool: [...]         # 症状关键词列表
  clue_map:                   # 口语化线索映射
    "症状": "患者口语表达"
  difficulty: 1               # 难度等级（1-3）
  persona_hints: {...}        # 患者人格化提示（可选）
```

### 多经典扩展预留

```yaml
source_classic 枚举值：
  - "伤寒论"
  - "金匮要略"
  - "温病条辨"    # 预留
  - "千金要方"    # 预留
  - "外台秘要"    # 预留
```

新增经典时，只需在 `source_article_map.md` 中追加条目，
Skill 自动识别 `source_classic` 字段并应用对应语境。

## 缺失记录机制

在构建/核对条文映射时，发现以下情况必须记录：

| 缺失类型 | 记录内容 | 写入位置 |
|---------|---------|---------|
| 有方无条 | 方剂在 formula_cards 中但无对应条文 | `docs/sp_missing_records.md` |
| 有条无方 | 条文提及方剂但 formula_cards 中无此卡 | `docs/sp_missing_records.md` |
| 编号待补 | article_number 为"待补充" | 优先补全，无法补全则记录 |
| 症状不符 | 条文症状与卡片 symptom_profile 冲突 | 标注矛盾，提交用户确认 |

每次核对完成后，在缺失记录文件中追加条目：
```markdown
## YYYY-MM-DD 核对记录
- [ ] 桂枝加厚朴杏子汤：条文编号待补（source_cards.json 中 article_number 为空）
- [ ] 麻黄杏仁甘草石膏汤：需确认对应条文第63条还是第162条
```

---

**答完第4点：前端控制 vs JSON 暴露配置的风险收益**

| 维度 | 前端自行控制 | JSON 中暴露配置 |
|---|---|---|
| 核心逻辑 | JSON 给完整数据，前端写 `if difficulty=1 then show 3 options` | JSON 中自带 `difficulty_config`，前端只按配置渲染 |
| 数据泄露风险 | ⚠️ **高**。困难模式的 L2 信息可能在 JSON 里，前端容易漏判 | ✅ **低**。JSON 里只有该难度允许的数据 |
| SP 口吻一致性 | 困难模式患者口吻应更隐晦，但前端控制模式下 AI 生成的是"标准口吻" | ✅ AI 生成时直接按难度决定口吻 |
| 无感升级难度 | 困难。前端改参数，但数据没变，学生"感觉"不到难度变化 | ✅ 简单。后端根据熟悉度动态改 `difficulty_config` |
| JSON 体积 | 较小（一套数据） | 稍大（每个难度独立生成） |
| 可维护性 | 差。难度逻辑分散在前后端 | 好。所有规则在 JSON 中自描述 |

**建议：JSON 中暴露配置，前端纯渲染。** 实现数据层、行为层、渲染层的三层解耦。无感升级难度时只需调整后端生成参数，前端完全不用改。

## 执行流程（快速参考）——JSON 输出模式

```
1. 用户触发 → 确定目标方剂/条文（或随机抽取）
2. 从 source_article_map.md 读取对应 article_entry
3. 从 persona_system.md 选择人格（v1.0 固定 anxious-middle-aged-female）
4. 生成完整 JSON 数据对象（严格遵循 json_schema.md）
   4.1 生成 patient + chief_complaint（按 directness 级别）
   4.2 生成 10 个 inquiry 方向（L1/L2/L3）
   4.3 生成 physical_exam（按 completeness 级别）
   4.4 预生成 case_summary（Markdown 纯文本）
   4.5 生成 question 选项（按 distractor_level 规则）
   4.6 填充 answer_key 和 reference_analysis
5. 输出 JSON → 前端接收并按字段渲染
   5.1 前端读取 difficulty_config → 控制问诊方向数、追问次数、L3 触发概率
   5.2 前端读取 inquiries → 展示可点击方向，按 L1/L2 梯度展示回答
   5.3 前端随机决定 L3 是否触发（按 probability）
   5.4 问诊结束后展示 case_summary + physical_exam
   5.5 展示 question.options → 学生选择
   5.6 比对 answer_key → 展示 reference_analysis（对照+反馈）
```

## 参考文献加载顺序

执行时按需加载：

1. **总是加载**：`references/source_article_map.md` — 核心数据
2. **生成主诉时**：`references/oral_expression_guide.md` — 口语化表达规范
3. **生成 JSON 时**：`references/json_schema.md` — 数据结构和约束
4. **选择人格时**：`references/persona_system.md` — 患者人格定义
5. **处理问诊时**：`references/ten_inquiries_framework.md` — 十问歌方向定义
6. **新增经典时**：`references/article_lookup_plan.md` — 查找计划与品质标准

## 关键提醒

- **本 Skill 不评判学生辨证水平**，只负责生成患者叙事和响应问诊
- 答案比对、评分、进度追踪由调用系统（如经方学习系统 app）处理
- 每次生成患者时，优先从 `source_article_map.md` 读取，确保与数据层一致
- 口语化表达必须参考 `oral_expression_guide.md`，禁止直接输出医学术语
