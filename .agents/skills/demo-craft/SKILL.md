# Demo Craft Skill — 交互 DEMO 制作规范

> 用户说「做个 demo」「做个界面看看」「设计一下呈现」时触发。

---

## 1. 触发条件

用户明确要求可视化呈现、交互演示、UI 示意时，走此流程。包括但不限于：

- "做个 demo 我看看"
- "设计一下这个界面"
- "这个交互你给我演示一下"
- "来一个能点的看看"
- "帮我设计这个功能的前端呈现"

### 1.1 元认知触发条件

除用户显式触发外，以下情况也应**自动触发**此 Skill：

| 条件 | 判断标准 | 示例 |
|------|----------|------|
| **交互逻辑复杂** | 涉及 2 步以上用户操作，或 3 种以上状态切换 | 标签系统（输入+添加+检索+过滤+渲染） |
| **用户需求模糊** | 用户描述场景但未指定具体 UI，需设计对齐 | "我想要一个记笔记的系统" |
| **数据模型需验证** | 存在多个可能的 Schema 方案，需用户选择 | 标签-笔记关系（多对多/一对多/标签分类方案） |
| **界面布局有歧义** | 同一功能可以有 3 种以上合理布局 | 对比视图（左右分栏/上下分栏/标签切换） |
| **技术方案待决策** | 实现方式不同，影响后续架构 | DEMO 用全前端 mock 还是走真实数据流 |

> 触发即走完整流程，不做「先试试再说」——设计对齐成本远低于改代码成本。

---

## 2. 第一步：设计对齐（必须）

动手之前，先对齐以下 5 个问题。输出在 DEMO 的 `README.md` 中。

### 对齐清单

| 问题 | 说明 |
|------|------|
| **目标** | 这个 DEMO 要验证什么假设？帮谁做什么决定？ |
| **用户场景** | 谁在用？在什么情境下？痛点是什么？ |
| **核心交互** | 用户点哪里 → 看到什么 → 感受到什么？用一句话说清。 |
| **数据需求** | 需要真实数据还是 mock？复杂度怎样？ |
| **不做什么** | 这个 DEMO 的边界在哪？哪些是故意不做的？ |

### 第一性原理追问

每次对齐时追问：

```
用户在这个场景下，最底层的需求是什么？
→ 去掉技术限制、去掉现有 UI 惯性，ta 真正想要什么？
→ 当前方案为什么满足不了？
→ 最简单的解法是什么？
```

### 对齐完成标志：输出「设计合约」

对齐完成后，必须在 DEMO 的 `README.md` 中以**表格形式**输出设计合约，用表格逐条列出关键设计决策。格式示例：

```markdown
## 设计合约（已确认）

| 条目 | 决定 |
|------|------|
| 标签作用对象 | 笔记（不是卡片） |
| 标签-笔记关系 | 多对多（一条笔记可打多个标签） |
| 标签添加方式 | 输入框 + 回车；支持批量粘贴 |
| 标签检索入口 | 统一在搜索栏 |
| 笔记 Markdown | 支持渲染 |
| 长文本处理 | 默认折叠，点击展开 |
| 笔记入口 | 条文面板 + 独立笔记列表页 |
```

**合约必须经用户确认后才能进入制作阶段。**

## 3. 第二步：输出产物

### 3.1 README.md（每个 DEMO 一份）

放在 `demos/<demo-name>/README.md`，包含：

```markdown
# DEMO：〈标题〉

## 设计对齐

- **目标**：
- **用户场景**：
- **核心交互**：
- **数据需求**：
- **不做什么**：

## 设计原则

- 原则 1：...
- 原则 2：...

## 交互流程

1. 用户看到什么
2. 用户做什么
3. 系统反馈什么

## 状态

- **阶段**：🟡 设计对齐中 / 🔵 已确认待实现 / 🟢 已实现 / ⚪ 已废弃
- **对应代码**：（如果有）`app/v9/src/xxx.js`
- **确认日期**：
```

### 3.2 index.html（可交互 DEMO）

- **单文件自包含** — 所有 HTML/CSS/JS 在一个文件中，不依赖外部资源
- **可交互** — 不是截图、不是 gif，是能点能看的页面
- **聚焦一个核心问题** — 不要大而全，只验证一个交互/流程/布局
- **文件路径**：`demos/<demo-name>/index.html`

### 3.3 登记到 DEMO INDEX

两个 INDEX 文件同时更新：

- `demos/INDEX.md` — AI 可读、命令行可查的文本版
- `demos/INDEX.html` — 浏览器打开的可视导航页

## 4. 存储与隔离规则

```
项目根目录/
├── demos/                    ← 所有 DEMO 的根目录
│   ├── INDEX.html            ← 浏览器导航页
│   ├── INDEX.md              ← 文本版索引
│   ├── archive/              ← 废弃 DEMO 移入（不删除）
│   │
│   ├── <demo-name>/          ← 每个 DEMO 一个文件夹
│   │   ├── index.html
│   │   └── README.md
│   └── ...更多 DEMO
│
├── app/                      ← 真实应用代码（与 demos/ 隔离）
├── data/
├── docs/
└── ...
```

### 隔离铁律

| 维度 | 规则 |
|------|------|
| **物理隔离** | `demos/` 与 `app/`、`data/`、`docs/` 同级，互不干涉 |
| **打包隔离** | 构建工具的 `build.input` 只指向 `app/` 入口，`demos/` 不参与打包 |
| **git 跟踪** | DEMO 正常进 git；废弃的移入 `demos/archive/`，不删除 |
| **上线边界** | `npm run build` / `vite build` 只产 `app/*/dist/`，`demos/` 不被引用 |

## 5. 从 DEMO 到代码的路径

用户确认 DEMO 后，进入编码阶段：

```
✅ 用户确认 DEMO
  │
  ├─ 更新 README.md 状态 → 🟢 已实现
  │
  ├─ 将交互逻辑翻译成真实组件代码
  │   ├─ 组件放 app/v9/src/components/
  │   ├─ 样式放 app/v9/src/styles/
  │   └─ 数据流整合到 AppStore / StorageService
  │
  ├─ 删除或保留 DEMO？
  │   ├─ 如果 DEMO 的交互已被真实代码完全覆盖 → 移入 demos/archive/
  │   └─ 如果 DEMO 仍有参考价值（展示设计过程）→ 保留在 demos/
  │
  └─ 登记 CHANGELOG
```

如果用户不确认，迭代回到第一步设计对齐。

### 5.1 回顾性抽象（迭代 ≥ 3 轮后自动执行）

如果 DEMO 经过 **3 轮以上迭代**（用户要求修改 ≥ 3 次），每次变更登记后自动执行一次回顾性抽象：

```
步骤 1：汇总变更历史
  逐条列出用户每次要求改了什么、原方案是什么、新方案是什么。

步骤 2：提取 Pattern
  从变更序列中提取 2-4 条设计 Pattern，例如：
  - 用户反复要求「简化」→ 提取为「渐进式信息呈递原则」
  - 用户反复要求「统一」→ 提取为「单入口聚合原则」
  - 用户反复要求「对比」→ 提取为「并排对比产出链接原则」

步骤 3：泛化到设计原则
  将 Pattern 改写为可复用的设计原则，以「原则 + 适用条件」格式输出：
  ```
  原则：XX
  条件：当需要 XXX 时
  验证方式：XXX
  ```

步骤 4：登记到设计模式库
  输出到对应的设计文档中（如 docs/设计模式库.md 或本项目设计总纲），
  并标注来源（如「提取自标签笔记系统 DEMO 迭代过程」）。
```

> **目的**：将单次 DEMO 的迭代经验转化为项目级可复用设计资产。
> **触发时机**：第 3 次变更登记完成时、第 5 次变更登记完成时、最终确认时。

### 5.2 部署与代码实现步骤

用户确认 DEMO 后，若明确要求「部署」或「改代码」，执行以下流程：

```
✅ 用户确认 DEMO 且要求部署
  │
  ├─ 步骤 1：完善 SKILL.md ← 先迭代 Skill（如果本次过程产生了新 Pattern）
  │
  ├─ 步骤 2：git commit + push
  │   ├─ 按规范提交（含 demos/ 变更 + SKILL.md 变更 + CHANGELOG 登记）
  │   └─ 提交信息格式：`feat(demos): 标签笔记系统 DEMO v2.0 + Skill 迭代`
  │
  ├─ 步骤 3：分析真实代码结构
  │   ├─ 扫描 app/v9/src/ 目录，理解已有组件、服务、路由
  │   └─ 识别 DEMO 中的交互逻辑应映射到哪些真实文件
  │
  ├─ 步骤 4：代码实现
  │   ├─ 存储层 → 对应 StorageService（或新建 NoteService）
  │   ├─ 组件层 → 对应 app/v9/src/components/
  │   ├─ 样式层 → app/v9/src/styles/theme.css
  │   └─ 集成层 → app/v9/src/app.js
  │
  ├─ 步骤 5：构建验证
  │   ├─ npm run build（无错误）
  │   └─ 浏览器冒烟测试（WebBridge 截屏确认）
  │
  └─ 步骤 6：再次 git commit + push
      ├─ 提交信息格式：`feat(v9): 笔记系统实现（NoteService + 浮窗 + 三入口）`
      └─ 更新 CHANGELOG
```

## 6. 命名规范

| 规则 | 示例 |
|------|------|
| DEMO 文件夹 | `条文笔记设计/` — 中文，表达功能或设计主题 |
| 文件名 | `index.html` / `README.md` — 固定名称 |
| 不要用 | `demo-v1/` `test/` `tmp/` — 无意义命名 |

## 7. 从 DEMO 到代码的映射模板

当 DEMO 确认后需要实现到真实代码时，用以下模板做结构化映射：

### 7.1 映射表

```markdown
## DEMO → 代码映射

| DEMO 模块 | 代码位置 | 职责 | 数据来源 | 依赖 |
|-----------|----------|------|----------|------|
| 标签输入 | `src/services/NoteService.js` | 标签 CRUD | localStorage | - |
| 笔记列表 | `src/components/NoteList.js` | 渲染+过滤 | NoteService | - |
| ... | ... | ... | ... | ... |
```

### 7.2 交互差异清单

列出 DEMO 与真实环境的差异点，避免直接照搬：

| 差异项 | DEMO 做法 | 真实环境做法 | 原因 |
|--------|-----------|-------------|------|
| 数据存储 | 硬编码 Mock | localStorage | 实际用户数据 |
| 路由 | 全部可见 | 页面切换 | 真实 app 结构 |
| ... | ... | ... | ... |

## 8. API / CLI 指令

用户触发词：

```
"做个demo" / "做个界面" / "设计一下" / "演示一下" / 
"来一个能点的" / "UI示意" / "交互演示" / "呈现一下"
```

检测到触发词后，立即走此流程：

1. 输出对齐问题
2. 等待用户确认
3. 制作 HTML + README
4. 更新 DEMO INDEX
5. 打开浏览器
6. 等待用户反馈 → 迭代或进入编码
