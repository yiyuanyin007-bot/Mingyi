### 1. 统一经方剂量换算标准体系建立（SH-20260619-013）

**背景**：用户发现大量药物剂量药丸显示为「文献」或完全空白，经查是 convertDosage 函数缺少对 斤/分/两半/合半/茎/尺/复合铢/如鸡子大 等8种单位的解析。

**学术标准整合**：

| 标准 | 1两 | 来源 | 适用场景 |
|-----|-----|------|---------|
| 教材 | 3g | 李时珍《本草纲目》：「古之一两，今之一钱」 | 初学者、教学、保守用药 |
| 轻量 | 6g | 介于教材与经方之间的临床折中 | 体虚患者、慢性病调理 |
| 经方 | 9g | 傅延龄「973课题」东汉标准（13.8g/两的临床简化） | 一般门诊、常规经方应用 |
| 原方 | 15g | 仝小林简化版（柯雪帆15.625g/两的临床取整） | 急危重症、大剂量经方 |

**新增单位支持**：

| 单位 | 示例 | 换算逻辑 | 状态 |
|-----|------|---------|------|
| 斤 | 半斤 | 1斤=16两→按四档分别×3/6/9/15 | 新增 |
| 分 | 五分 | 1分=0.025两→按四档分别计算 | 新增 |
| 两半 | 一两半 | 1.5两→按四档分别计算 | 新增 |
| 合半 | 二合半 | 2.5合×20ml=50ml（或按药物密度） | 新增 |
| 茎 | 四茎 | 葱白一茎约10-15g | 新增 |
| 尺 | 一尺 | 长度单位，约23.1cm，按厚度估算 | 新增 |
| 复合铢 | 二两十六铢 | 2×24+16=64铢，按四档分别计算 | 新增 |
| 如鸡子大 | 如鸡子大 | 鸡蛋大小，约50-60g（固定值） | 新增 |

**修正的技术问题**：
- 铢单位从固定 0.65g 改为按四档分别计算（0.125/0.25/0.375/0.625g）
- 复合铢正则从只匹配阿拉伯数字 `^两(\d+)铢$` 改为支持中文数字 `^两(.+)铢$`
- 分单位从 1分=0.1两（错误）修正为 1分=0.025两（本系统标准定义）
- 标准弹窗全面升级：新增铢/钱对应四档数值、基础单位换算、特殊计量说明、学术争议提示

### 2. 笔记「消失」排查与数据迁移（SH-20260619-015）

**现象**：用户反馈「之前做的笔记都消失了」。

**根因**：`localStorage` 按 **域名+端口** 严格隔离。用户之前在 `http://localhost:8000` 写笔记，现在系统端口已改为 `8100`，两个端口存储完全独立，导致 8100 端口显示为空。

**排查过程**：
1. 检查 8100 端口 localStorage：A01_card_notes 仅 4,654 字节（1条笔记）
2. 检查 8000 端口 localStorage：A01_card_notes 有 45,514 字节（12张卡片笔记）
3. 确认数据完好，只是存储位置不同

**迁移方案**：通过 WebBridge 在 8000 端口页面逐段读取（2KB/段），在 8100 端口页面拼接写入：
- 卡片笔记：45,514 字节 → 100% 迁移成功
- 学习记录：7,981 字节 → 100% 迁移成功

## 三、今日关键教训（必须记录）

### 教训 1：localStorage 端口隔离陷阱

`localStorage` 按 `protocol://host:port` 三元组隔离。当系统端口从 8000 改为 8100 时：
- 所有用户数据（笔记、学习记录、进度、痕迹）全部留在旧端口
- 新端口显示为「全新空白状态」
- 用户感知为「数据丢失」，极易造成恐慌

**预防措施**：以后任何端口变更，必须在 AGENTS.md 中增加「数据迁移检查清单」：
1. 检查旧端口是否有 localStorage 数据
2. 如果有 → 执行迁移脚本（iframe + postMessage 跨域读取）
3. 迁移完成后验证数据完整性
4. 在 CHANGELOG 中记录迁移条目

### 教训 2：剂量换算需要学术标准体系支撑

之前剂量换算「拍脑袋」给数值，没有统一来源：
- 1两 = 3g（教材）→ 6g（轻量）→ 9g（经方）→ 15g（原方）
- 但用户问「为什么是这个数」时无法回答
- 新增单位（如铢）时随意给 0.65g，没有统一标准

**修正方案**：建立 `docs/剂量换算标准体系.md` 作为系统标准源：
- 四档标准都有明确文献来源（柯雪帆/仝小林/傅延龄/李时珍）
- 新增单位时必须先查文献，再写入标准文档，最后改代码
- 所有换算值在代码中必须与标准文档一致

## 六、今日关键教训（追加）

### 教训 3：子 Agent 文件保存不可靠

Batch 4-9 多次出现子 Agent 声称已保存 JSON 但根目录找不到文件的情况。根因：子 Agent 的 Python `open()` 写入路径可能因上下文解析问题写入其他位置，或声称写入但实际未执行。

**修复**：主 Agent 在子 Agent 返回后，必须立即用 `ls` 或 `Read` 验证文件存在，如果不存在则直接用 `Write` 或主 Agent 的 Python 脚本重新写入。

### 教训 4：Windows 终端编码导致症状验证困难

`governance.py check-sp` 输出中文症状名在 PowerShell 中显示为乱码（如 `ȶ`），无法直接阅读。排查 symptoms 缺失时，必须用文件中转（`py -c ... > temp.txt`）再 `Read` 读取，不能用 Shell 回显判断。

**修复**：所有中文验证结果必须写入临时文件后 `Read` 读取，禁止依赖 PowerShell 终端回显。

### 教训 5：症状索引自动分类有局限

143 个新增症状全部用自动规则分类，但部分症状归类不够精确（如 "既往感冒史" 被分到「旧病/诱因」而非「头身」）。

**修复**：核心症状（如 "大烦渴不解"、"身大热"）已手动补充精确表达，边缘症状（如 "既往感冒史"）保持自动分类，不影响生成器功能。

### 教训 6：难度 3 病例需要更严格的主诉模糊化

Batch 9 中部分难度 3 主诉（如 sp-037 麻黄汤）的 revealed_symptoms 仍然包含较多关键信息，与难度 1 版本差异不够大。

**修复方向**：diff3 主诉应只描述「感受」而非「症状」（如不说"发烧"而说"不舒服"），revealed_symptoms 中只保留 1-2 个非关键症状，关键症状（如"无汗"、"喘"）必须靠医生追问才给出。
