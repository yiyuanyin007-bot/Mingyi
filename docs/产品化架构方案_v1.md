## 一、产品定位重塑：从"个人工具"到"认知训练系统"

### 1.1 不是做什么

| 误区 | 原因 |
|------|------|
| ❌ "伤寒论背诵APP" | 市面上已有数十款，无差异化 |
| ❌ "中医词典/查询工具" | 一次性使用，无用户粘性 |
| ❌ "在线课程平台" | 需要持续内容生产，重运营 |
| ❌ "电子病历系统" | 需医疗资质，合规门槛高 |

### 1.2 应该做什么

**产品名建议**：《经方认知训练系统》/《经方炼金》/《方证映射》

**一句话定位**：
> 用学习科学和认知工程，把"背伤寒论"变成"训练临床思维"的系统。

**核心价值主张**：
- **对学习者**：不是给你资料，是给你一套"怎么学"的方法——八向量训练、症状三分法、SP信息分层、循证审计，全部可执行
- **对建造者**：展示一个人如何用工程思维+AI协作，把混乱的知识材料炼成结构化系统
- **对中医教育**：填补了"条文背诵"到"临床辨证"之间的训练空白

### 1.3 差异化壁垒

| 市面上产品 | 本系统 |
|-----------|--------|
| 单向背诵（方名→药物→症状） | 双向映射（6向量+关联学习） |
| 静态卡片 | 掌握度追踪+SRS复习调度 |
| 无反馈或简单对错 | 认知诊断标签（类方混淆/反向盲区/知识缺口/决策失误） |
| 无临床模拟 | 标准化病人（L0→L3信息分层） |
| 无证据验证 | 循证审计（文献检索→GRADE评级→验证闭环） |
| 个人使用 | 数据飞轮（使用数据→反馈→优化→出版） |

### 3.2 分阶段技术路线

#### Phase 1：PWA MVP（0-2个月）

**目标**：让现有系统能在手机上好用，能离线使用，可安装到主屏

**技术栈**：
- 前端：基于现有v9组件化骨架，补全缺失组件
- 构建：Vite + PWA插件（vite-plugin-pwa）
- 数据：localStorage + IndexedDB（离线缓存）
- 部署：GitHub Pages / Netlify / Vercel（免费）

**关键工作**：
1. 完成v9组件化：把v8中缺失的SP、Clinical、SourcePanel、SlidePanel等功能迁移到v9
2. 补全mobile体验：响应式设计 + 触摸手势 + 底部导航
3. 添加PWA能力：Service Worker + Manifest + 离线缓存
4. 数据持久化升级：从localStorage迁移到IndexedDB（容量更大，支持结构化查询）
5. 部署到静态托管：一键构建+自动部署

**交付物**：
- 一个可安装到手机主屏的PWA
- 支持离线使用（全部63方+398条条文本地缓存）
- 与v8功能对等

#### Phase 2：云端同步+用户体系（2-4个月）

**目标**：跨设备同步学习进度，建立用户身份

**技术栈选择**：

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **Supabase**（推荐） | PostgreSQL+Auth+Realtime，开源，可自建，免费 tier 够用 | 需要学习成本 | ⭐⭐⭐⭐⭐ |
| Firebase | 生态成熟，Google背书，Realtime Database | 国内访问不稳定，vendor lock-in | ⭐⭐⭐⭐ |
| 自建后端（Node.js/Go） | 完全自主可控，无平台依赖 | 开发成本高，需运维 | ⭐⭐⭐ |
| 微信小程序云开发 | 国内生态好，与小程序天然集成 | 仅限微信生态 | ⭐⭐⭐⭐ |

**推荐方案：Supabase**
- 理由：开源、可自建（避免vendor lock-in）、PostgreSQL支持JSONB（完美适配现有JSON结构）、Auth支持多种登录方式、Realtime支持订阅（学习进度同步）
- 免费 tier：500MB数据库 + 1GB存储 + 2GB带宽，足够MVP阶段

**关键工作**：
1. 设计数据库Schema（从JSON结构映射到关系型表）
2. 实现用户注册/登录（邮箱+密码 / 微信OAuth / 匿名登录）
3. 实现数据同步引擎：本地↔云端冲突解决（last-write-wins + 手动合并）
4. 实现SRS复习调度的服务端计算（支持跨设备一致性）
5. 部署：Vercel（前端）+ Supabase（后端）+ Cloudflare（CDN）

**交付物**：
- 用户可在多设备上同步学习进度
- 匿名试用 + 注册登录后同步
- 服务端统计（六经覆盖度、学习曲线等）

#### Phase 3：微信小程序（3-5个月）

**目标**：进入中国最大用户池，利用社交裂变

**技术栈**：
- 框架：Taro 3（React语法，可编译到微信小程序）或 uni-app（Vue语法，多端输出）
- 推荐：Taro 3，因为v9基于React/Vite风格，迁移成本更低
- 云开发：微信小程序云开发（数据库+云函数+存储）或对接自建Supabase

**关键工作**：
1. 复用v9组件：80% UI组件可复用（Taro兼容React组件）
2. 适配微信小程序限制：包大小2MB限制（需要分包加载）、部分CSS不支持
3. 实现微信登录：一键授权，零 friction
4. 分享功能：卡片分享（"我今日复习了桂枝汤，来挑战我？"）、排行榜
5. 支付：微信支付接入（订阅制）

**交付物**：
- 微信小程序上线（"经方训练"或"方证映射"）
- 支持微信分享、排行榜、好友PK
- 与Web端数据互通（同一Supabase后端）

#### Phase 4：原生APP（Flutter）（6-12个月）

**目标**：最佳性能体验，推送通知，深度系统集成

**技术栈**：
- 框架：Flutter（Dart）
- 理由：一套代码同时编译iOS+Android，UI高度自定义，性能接近原生
- 替代：React Native（JS生态，但v9是React，迁移更顺）
- 推荐：Flutter（UI一致性更好，中医学习应用需要大量自定义图表和动画）

**关键工作**：
1. 设计Flutter版UI（Material 3 + 中医传统色）
2. 实现离线包：全量数据本地存储，无需网络即可使用
3. 推送通知：每日复习提醒、新内容推送
4. 深度集成：日历集成（学习打卡）、健康数据（可选）
5. 应用商店上架：App Store + Google Play + 国内应用商店

**交付物**：
- iOS/Android 原生APP
- 支持推送、离线、深度系统集成
- 与Web/小程序数据互通

## 四、数据架构演进

### 4.1 从JSON到数据库的映射

**现有JSON结构** → **PostgreSQL Schema**

```sql
-- 方剂表
CREATE TABLE formulas (
  id TEXT PRIMARY KEY,          -- "gui-zhi-tang"
  name TEXT NOT NULL,           -- "桂枝汤"
  formula_name TEXT NOT NULL,
  role TEXT,                    -- "主方"
  description TEXT,
  chapter TEXT,                 -- "太阳病篇"
  tags TEXT[],                  -- ["太阳病", "解表剂"]
  source_text TEXT,             -- 原文
  pathology TEXT,               -- 病机
  usage TEXT,                   -- 煎服法
  core_combinations TEXT,       -- 核心药对
  core_rationale TEXT,          -- 药对 rationale
  created_at TIMESTAMPTZ,
  updated_at TIMESTAMPTZ
);

-- 药物表
CREATE TABLE herbs (
  id SERIAL PRIMARY KEY,
  formula_id TEXT REFERENCES formulas(id),
  name TEXT NOT NULL,           -- "桂枝"
  dosage TEXT,                  -- "三两"
  dosage_grams NUMERIC[],       -- [9, 18, 27, 45] -- 四标准
  order_index INT
);

-- 症状表
CREATE TABLE symptoms (
  id SERIAL PRIMARY KEY,
  formula_id TEXT REFERENCES formulas(id),
  symptom TEXT NOT NULL,        -- "汗出"
  type TEXT,                    -- "necessary" | "common" | "excluding"
  order_index INT
);

-- 条文表
CREATE TABLE source_articles (
  id TEXT PRIMARY KEY,          -- "article-001"
  chapter TEXT NOT NULL,          -- "太阳病篇"
  article_number TEXT NOT NULL,   -- "1"
  text TEXT NOT NULL,             -- 原文
  symptoms TEXT[],
  mentioned_formulas TEXT[]
);

-- 方-文关联表
CREATE TABLE formula_article_links (
  formula_id TEXT REFERENCES formulas(id),
  article_id TEXT REFERENCES source_articles(id),
  PRIMARY KEY (formula_id, article_id)
);

-- 用户表
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT UNIQUE,
  phone TEXT UNIQUE,
  display_name TEXT,
  avatar_url TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  subscription_tier TEXT DEFAULT 'free'  -- 'free' | 'pro' | 'expert'
);

-- 用户掌握度表
CREATE TABLE user_mastery (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id),
  formula_id TEXT REFERENCES formulas(id),
  vector_type TEXT,               -- '0→1' | '1→0' | '0→2' | '2→0' | '0→usage' | '0→contra'
  level INT DEFAULT 0,            -- 0-5
  streak INT DEFAULT 0,
  total_attempts INT DEFAULT 0,
  correct_count INT DEFAULT 0,
  next_review TIMESTAMPTZ,
  last_attempted TIMESTAMPTZ,
  UNIQUE(user_id, formula_id, vector_type)
);

-- 学习记录表
CREATE TABLE study_sessions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES users(id),
  session_type TEXT,              -- 'practice' | 'exam' | 'daily_review' | 'sp'
  started_at TIMESTAMPTZ,
  ended_at TIMESTAMPTZ,
  total_questions INT,
  correct_count INT,
  data JSONB                      -- 详细记录（每题的对错、用时、诊断标签）
);

-- SP病例表
CREATE TABLE sp_cases (
  id TEXT PRIMARY KEY,
  difficulty INT,                 -- 1-3
  mode TEXT,                      -- 'article' | 'formula'
  formula_id TEXT REFERENCES formulas(id),
  article_id TEXT REFERENCES source_articles(id),
  patient_json JSONB,             -- 患者信息
  chief_complaint JSONB,          -- 主诉
  inquiries JSONB,                -- 问诊方向
  answer_key JSONB,               -- 答案
  is_premium BOOLEAN DEFAULT FALSE  -- 付费病例
);

-- 循证审计报告表
CREATE TABLE evidence_audits (
  id TEXT PRIMARY KEY,
  formula_id TEXT REFERENCES formulas(id),
  status TEXT,                    -- 'pending' | 'auditing' | 'verified' | 'corrected'
  report_markdown TEXT,
  references JSONB,               -- 参考文献列表
  grade_ratings JSONB,           -- GRADE评级
  created_at TIMESTAMPTZ,
  updated_at TIMESTAMPTZ
);
```

### 4.2 数据同步策略

```
本地（IndexedDB）          云端（Supabase）
     │                          │
     │  1. 用户操作（答题/记笔记）  │
     │ ─────────────────────────> │
     │  2. 本地先更新（乐观更新）   │
     │  3. 后台同步队列            │
     │  4. 网络可用时同步          │
     │ ─────────────────────────> │
     │  5. 冲突检测                │
     │ <───────────────────────── │
     │  6. 冲突解决（last-write-wins）│
     │  7. 本地状态更新            │
     │                          │
     │  8. 其他设备登录时拉取        │
     │ <───────────────────────── │
```

**冲突解决规则**：
1. 掌握度数据：以最高`level`和最新`next_review`为准
2. 学习笔记：以最新`updated_at`为准，保留历史版本
3. 错题本：合并去重，保留所有记录
4. 临床档案：独立标识，不合并

### 7.2 设计系统（Design System）

**品牌色**：
- 主色：赭石 `#C17F59`（中医传统色，温暖、沉稳）
- 辅色：黛青 `#4A6741`（条文/原文的古典感）

- 正文：思源黑体（Noto Sans SC）—— 可读性

- 卡片：圆角8px，米白背景，淡赭石边框

- 标签：药丸式（与现有v8一致）
- 弹窗：毛玻璃效果，从底部滑入（移动端）

## 十、架构师总结

### 核心判断

1. **产品化不是重写，是重塑**：现有63方+398条条文+SP+循证审计的内容资产极其厚实，远超一般MVP。最大的工作不是"做内容"，而是"把内容包装成产品"。

2. **方法论是最大壁垒**：八向量、症状三分法、SP信息分层、循证审计——这些不是功能，是**思想体系**。出版内容建立思想领导力，产品功能让思想可执行。

3. **PWA是最佳起点**：零成本、跨平台、可离线、可安装。不要一上来就做APP，先让PWA跑起来，验证用户价值，再逐步扩展。

4. **出版与产品互为飞轮**：书中讲故事（"我为什么做这个系统"），产品让故事可体验（"你来试试这个系统"）。用户数据反哺出版（"10,000人的学习数据证明了八向量的有效性"）。

5. **中医学习市场的真实需求**：不是"更多资料"，是"不知道怎么学"。本系统的差异化恰恰在于"教你怎么学"——八向量训练的是学习方法，不是内容本身。

### 建议的下一步

**本周**：完成PWA部署，让现有系统可以作为一个可安装的应用使用。这是最低成本、最高价值的第一步。

**本月**：基于用户反馈，确定产品名和核心卖点，完成v9的组件化补全（把v8中缺失的SP、Clinical等功能迁移）。

**本季度**：上线微信小程序，利用出版联动进行冷启动，积累首批1000名种子用户。
