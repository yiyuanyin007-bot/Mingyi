# 经方学习系统 · 工程化重构顶层设计（自动化 LOOP 引擎）

> **版本**：v2.1 · 自动化循环 + 双文档透明版  
> **核心设计**：AI 自动推进，人在「可完整测试阶段」验收、给反馈，反馈决定下一轮方向。  
> **沟通规则**：所有选项呈现为「风险 / 收益」而非「选 A 还是选 B」。  
> **决策点**：只在用户必须做决定时暂停，用户只说「走」或「停」或「调整方向」。  
> **文档双轨**：每个 ROUND 产出两份文档——`ROUND-N-engine.md`（机器执行）+ `ROUND-N-human.md`（人话翻译），保证机器执行对人类透明。

## 〇、双文档透明机制（新增）

### 〇.1 为什么需要双文档？

| 问题 | 单文档（纯工程） | 双文档（工程 + 人话） |
|------|------------------|----------------------|
| 用户看不懂 | 满篇代码、函数名、路径，用户不知道 AI 在干嘛 | 人话文档告诉用户「刚才做了什么事」「对系统有什么影响」 |
| 反馈质量低 | 用户只能给模糊反馈如「不太对」 | 用户知道具体改了什么，反馈精准如「经验卡数量不对」 |
| 信任感不足 | 黑盒执行，用户不知道有没有偷工减料 | 透明化，每个动作都有对应的人话解释 |
| 后续维护难 | 只有工程师能看懂记录 | 任何参与者都能理解历史决策 |

### 〇.2 双文档分工

| 维度 | `ROUND-N-engine.md`（机器） | `ROUND-N-human.md`（人话） |
|------|----------------------------|---------------------------|
| **读者** | AI 助手、后续开发者、代码审查 | 用户（陈医生）、产品经理、非技术协作者 |
| **内容** | 函数清单、代码行数、测试结果、schema 验证、覆盖率 | 「做了什么」「为什么做」「做完能干什么」「人在哪个阶段该出现」 |
| **格式** | 表格、代码块、量化指标、通过/失败 | 叙事体、类比、流程图、用例场景 |
| **语言** | 技术术语（innerHTML、DOM、Service、Store） | 日常用语（显示方式、答题流程、保存进度） |
| **长度** | 详尽，不遗漏任何工程细节 | 精简，聚焦「可感知的变化」 |
| **更新时机** | 每完成一个工程步骤实时追加 | 每完成一个用户可感知阶段后统一编写 |

### 〇.3 人话翻译的标准模板

每个 `ROUND-N-human.md` 必须包含以下 6 个板块：

```markdown
# ROUND N 人话翻译 · {阶段名称}

## 1. 本轮在做什么？（一句话）
{用日常语言描述本轮目标，不超过 50 字}

## 2. 为什么现在做这件事？（背景）
{解释这个问题如果不解决会怎样，解决后会带来什么好处}

## 3. 机器具体做了什么？（动作清单）
{把 engine.md 中的技术动作翻译成人话}
| 机器动作 | 人话翻译 | 对系统的影响 |
|----------|----------|--------------|
| 提取 `utils/formatters.js` | 把「名字转换」这类小工具单独收进一个工具箱 | 以后任何地方需要「名字转换」都能直接调用，不用重复写 |

## 4. 做完之后，系统现在能干什么？（能力变化）
{列出用户现在能感知到的功能变化，如「刷新页面进度不丢」}

## 5. 人在哪个阶段该出现？（暂停点）
{明确告诉用户什么时候需要他测试、给反馈、做决策}

## 6. 已知问题与下一步（诚实披露）
{不隐瞒问题，用直白语言说明还有什么没做好、下轮要做什么}
```

### 〇.4 透明化承诺

以下内容是**必须**翻译的，不得遗漏：

1. **所有「innerHTML」相关的改动** → 翻译成「页面内容的显示方式」
2. **所有「状态管理」改动** → 翻译成「答题记录和进度怎么保存」
3. **所有「测试」相关** → 翻译成「怎么确认这个功能没坏」
4. **所有「架构/目录」改动** → 翻译成「文件怎么归类，以后找东西去哪找」
5. **所有「数据校验」** → 翻译成「卡片内容有没有错」
6. **所有「性能/加载」** → 翻译成「打开页面快不快、卡不卡」

## 二、ROUND 定义：一个完整循环

### 2.1 ROUND 内部结构

每个 ROUND 由以下 5 个步骤自动执行，直到用户确认「暂停」：

| 步骤 | AI 动作 | 用户动作 | 产出物 |
|------|--------|----------|--------|
| **1. 目标设定** | 根据上一 ROUND REVIEW 产出或初始目标，定义本轮可交付的功能块 | 确认或调整目标 | `ROUND-N-goal.md` |
| **2. 自动执行** | 按任务清单自动执行，每完成一项更新进度 | 旁观（可选查看进度） | 代码 + 测试 + 文档 |
| **3. 自验证** | 自动运行测试、截图对比、数据校验、冒烟检查 | 旁观 | 验证报告 |
| **4. 交付报告** | 输出：做了什么、验证结果、已知问题、下一步建议 | **决策**：继续 / 暂停 / 回退 | `ROUND-N-report.md` |
| **5. 经验沉淀** | 自动将本轮踩的坑、决策逻辑、验证方法写入知识库 | 补充或修正 | `docs/LOOP-rounds.md` |

### 2.2 关键暂停点（Pause Point）

一个 ROUND 在以下两种情况下自动暂停，等待用户验收：

1. **功能块可完整测试**：用户能用浏览器打开、点击、考试、复习，感受真实体验。
2. **出现无法自动解决的决策**：需要用户在多个路径中选择。

暂停时 AI 的输出格式：

```
【ROUND N 暂停】

当前可测试内容：
- [ ] 功能 A：...
- [ ] 功能 B：...

测试入口：http://localhost:8000/app/v9/...

本轮发现的问题：
1. ...（已自动修复 / 待确认）

需要你的决策：
【选项 1】继续推进 ROUND N+1，目标：...
  → 收益：...
  → 风险：...

【选项 2】回溯到 ROUND N-1，调整：...
  → 收益：...
  → 风险：...

【选项 3】冻结当前进度，手动修复问题 X
  → 收益：...
  → 风险：...

请回复：走 1 / 走 2 / 走 3 / 或补充反馈
```

## 三、沟通协议：风险/收益呈现

### 3.1 禁止的说法

| ❌ 旧说法 | ✅ 新说法 |
|----------|----------|
| "用 Vite 还是 Parcel？" | "Vite 收益：零配置、HMR 快、生态大；风险：构建产物可能不如 Parcel 精简。Parcel 收益：更智能的零配置；风险：HMR 慢、社区活跃度下降。建议 Vite，你确认？" |
| "目录放 app/v9/ 还是独立项目？" | "app/v9/ 收益：保持统一入口、现有脚本不用改；风险：新旧代码混在同一个 repo，长期可能杂乱。独立项目收益：完全隔离、可独立发版；风险：数据同步需要额外脚本。建议 app/v9/，你确认？" |
| "TypeScript 要不要？" | "不用 TS 收益：零编译、直接用浏览器打开、门槛最低；风险：没有类型检查，重构时可能漏掉接口变更。用 TS 收益：类型安全、IDE 提示强；风险：需要构建步骤、对新手维护者增加认知负担。建议不用 TS，用 JSDoc 补充类型提示，你确认？" |

### 3.2 决策模板

每个需要用户做决策的地方，使用统一模板：

```markdown
## 决策点：{问题简述}

### 背景
{为什么现在需要做这个决策}

### 方案 A：{简述}
- **收益**：{1} / {2} / {3}
- **风险**：{1} / {2} / {3}
- **适用条件**：{什么时候这个方案最好}

### 方案 B：{简述}
- **收益**：{1} / {2} / {3}
- **风险**：{1} / {2} / {3}
- **适用条件**：{什么时候这个方案最好}

### 我的建议
{建议方案}，因为 {核心理由}。

### 请确认
回复「走 A」或「走 B」或「补充：...」
```

## 四、质量控制体系

### 4.1 三层自动验证

每个 ROUND 结束时自动运行，无需人工：

| 层级 | 验证内容 | 自动修复 | 阈值 |
|------|----------|----------|------|
| **L1 代码** | ESLint 规则、`innerHTML` 扫描、全局变量扫描 | 纯格式问题自动修复 | 0 违规 |
| **L2 测试** | 单元测试 + 集成测试 | 不涉及 | 核心 Services 100% 通过，单元 ≥ 70% |
| **L3 功能** | 冒烟测试（Playwright 复刻 v8 流程）+ 截图对比 | 不涉及 | 6 步流程 100% 通过，截图差异 < 2% |

### 4.2 数据质量门禁

每次数据变更自动运行：

| 检查项 | 自动脚本 | 失败时动作 |
|--------|----------|------------|
| JSON schema 合规 | `scripts/validate_schema.py` | 阻断提交，输出错误位置 |
| 字段完整率 | `scripts/check_completeness.py` | 输出缺失字段清单，不阻断（标记黄色） |
| 别名冲突 | `scripts/check_aliases.py` | 阻断提交，输出冲突项 |
| 去重检查 | `scripts/check_duplicates.py` | 阻断提交，输出重复项 |
| 来源链接可访问 | `scripts/check_links.py`（抽样） | 输出 404 清单，不阻断（标记红色） |

### 4.3 经验沉淀机制

每个 ROUND 结束后自动追加到 `docs/LOOP-rounds.md`：

```markdown
## ROUND 3 · 2026-06-20

### 目标
提取 CardList + LearnView 组件，接入 Store。

### 执行摘要
- 完成：CardList 纯渲染组件提取，props 驱动
- 完成：LearnView 内容切换逻辑迁移到 AppStore
- 发现问题：原 `index.html` 中 `currentCardIdx` 同时用于 UI 渲染和考试状态，需要拆分为两个状态
- 已修复：拆分为 `ui.activeCardId` 和 `exam.currentCardId`

### 验证结果
- 单元测试：78% 通过（> 70% 阈值）✅
- 集成测试：CardList + LearnView 联动通过 ✅
- 截图对比：与 v8 左侧栏差异 0.8%（< 2% 阈值）✅
- 冒烟测试：步骤 1-3 通过，步骤 4（localStorage 持久化）失败 ❌

### 已知问题
1. localStorage 迁移后 `mastery` 字段丢失（原因：旧键名是中文箭头，新 schema 是对象结构）
2. 建议下轮修复：StorageService 增加旧数据兼容层

### 用户反馈（暂停时收集）
- 用户：「CardList 的卡片字体比原来小了一点」
- 已确认：CSS 变量 `--card-font-size` 从 16px 误设为 14px，已自动修复

### 决策记录
- 选择「拆分两个状态」而非「保留一个状态」：收益是职责分离清晰；风险是多了 1 个状态需要同步。

### 下轮目标（根据反馈和验证结果）
1. 修复 localStorage 迁移兼容层
2. 提取 ExamView 组件
3. 接入 ExamService 出题逻辑

### 经验沉淀
- 状态拆分时要检查所有读取点，避免遗漏
- CSS 变量提取后要与原稿像素级对比，不只是逻辑对比
```

## 五、反馈闭环协议

### 5.1 用户反馈收集表

每个暂停点，用户可以用任何方式给反馈，AI 自动结构化：

```markdown
| 反馈类型 | 用户原话 | AI 结构化理解 | 对应行动 |
|----------|----------|---------------|----------|
| 体验问题 | "考试界面卡了一下" | 性能问题：考试页面渲染可能有阻塞 | 下轮增加性能埋点，检查是否 innerHTML 大批量操作导致 |
| 功能缺失 | "想导出我的学习进度" | 需求：导出 localStorage 数据为 JSON | 下轮目标：增加 StorageService.export() |
| 数据问题 | "大青龙汤的禁忌没写" | 数据缺失：大青龙汤 canonical.contraindications 为空 | 下轮检查数据质量门禁，补充禁忌 |
| 体验偏好 | "颜色太淡了看不清" | 视觉偏好：主题色对比度不足 | 下轮调整 CSS 变量，增加对比度 |
| 决策意见 | "不要先弄考试，先把每日复习做完整" | 优先级调整：ROUND 目标重新排序 | 下轮目标调整：先做 DailyReview，后做 ExamView |
```

### 5.2 反馈 → 下一轮目标的映射规则

1. **体验问题**：进入下轮目标「修复 + 回归测试」。
2. **功能缺失**：进入下轮目标「新增 + 测试覆盖」。
3. **数据问题**：立即修复数据，进入下轮目标「数据质量门禁补全」。
4. **体验偏好**：记录到 `docs/LOOP-preferences.md`，下轮目标中调整对应组件。
5. **决策意见**：直接调整下轮目标排序，无需额外解释（用户有最终决策权）。

## 六、自动化执行清单（每个 ROUND 的 AI 动作）

### 6.1 ROUND 0: 盘点（Leverage）

**目标**：建立可量化的现状基线。

**自动执行**：
- [ ] 审计 `app/index.html`：提取所有全局变量、函数、DOM 操作、事件监听
- [ ] 审计 `data/*.json`：schema 字段覆盖率、缺失值、类型一致性
- [ ] 生成函数依赖图（哪些函数调用了哪些）
- [ ] 生成「功能矩阵」：每个功能对应哪些函数/数据/事件
- [ ] 生成 `localStorage` 结构解析 + 迁移方案草案
- [ ] 输出报告：`docs/ROUND-0-report.md`

**暂停点**：报告输出后，用户确认基线是否完整。

### 6.2 ROUND 1: 骨架（Organize）

**目标**：产出可编译、可运行的空架构。

**自动执行**：
- [ ] 创建 `app/v9/` 目录结构
- [ ] 配置 Vite（vite.config.js）
- [ ] 配置 Vitest（vitest.config.js）
- [ ] 配置 Playwright（playwright.config.js）
- [ ] 实现 `DataService` mock（读取本地 JSON）
- [ ] 实现 `StorageService` mock（localStorage 抽象）
- [ ] 实现 `AppStore`（最小状态树）
- [ ] 跑通 `npm run dev`（浏览器能打开空白页面）
- [ ] 跑通 `npm run test`（至少一个测试通过）
- [ ] 输出报告：`docs/ROUND-1-report.md`

**暂停点**：浏览器能打开 `http://localhost:5173/app/v9/` 显示空白页面，用户确认架构入口是否合理。

### 6.3 ROUND 2: 核心（Operate·Phase 1-3）

**目标**：工具函数 + 数据服务 + 状态管理，全部可测试。

**自动执行**：

### 6.4 ROUND 3: 界面（Operate·Phase 4-5）

**目标**：可完整测试的界面，用户能真实使用。

## 八、决策点清单（全局）

以下是整个 LOOP 过程中所有需要用户做决策的点，按风险/收益呈现：

### 决策点 1：启动时机

- **现在启动**：收益：临床数据还没大量积累，重构不会丢失太多用户数据；风险：重构期间不能开发新功能。
- **等临床数据积累后启动**：收益：有真实数据驱动重构；风险：用户进度数据更多，迁移更复杂。
- **建议：现在启动**。用户确认？

### 决策点 2：新架构目录位置

- **app/v9/**：收益：统一入口、数据符号链接简单、现有脚本不用改；风险：新旧代码混在同一个 repo，长期可能杂乱。
- **独立项目（shanghanlun-v9/）**：收益：完全隔离、可独立发版、新协作者门槛更低；风险：需要额外数据同步脚本，可能产生两个 truth source。
- **建议：app/v9/**。用户确认？

### 决策点 3：TypeScript

- **不用 TS**：收益：零编译、直接用浏览器打开、门槛低、与现有代码风格一致；风险：重构时接口变更可能漏掉，没有类型安全网。
- **用 TS**：收益：类型安全、IDE 提示强、重构更自信；风险：需要构建步骤、增加认知负担、可能需要改写现有数据类型定义。
- **建议：不用 TS，用 JSDoc + `.d.ts` 做类型提示**。用户确认？

### 决策点 4：构建工具

- **Vite**：收益：零配置、HMR 极快、社区最大、与 Vitest 原生集成；风险：构建产物可能比 Rollup 大几十 KB（对 500MB 项目可忽略）。
- **Parcel**：收益：理论上更智能的零配置；风险：社区活跃度下降、HMR 慢、调试体验不如 Vite。
- **无构建工具（保持单文件）**：收益：最简单；风险：无法做模块化、无法做 tree-shaking、无法引入测试框架。
- **建议：Vite**。用户确认？

### 决策点 5：测试框架

- **Vitest + Playwright**：收益：Vite 原生集成、速度快、API 与 Jest 相似；风险：需要额外学习 Playwright（但学习成本很低）。
- **Jest + Puppeteer**：收益：更成熟、文档更多；风险：与 Vite 集成需要额外配置，速度慢。
- **无测试框架（手动冒烟）**：收益：零成本；风险：回归只能靠人，不可靠。
- **建议：Vitest + Playwright**。用户确认？

### 决策点 6：移动端策略

- **合并为响应式 index.html**：收益：一套代码维护、用户无感知切换；风险：需要重新设计断点布局，工作量更大。
- **保留独立 mobile.html**：收益：快速同步现有 mobile.html 内容；风险：两套代码长期 divergence，维护成本翻倍。
- **建议：合并为响应式**。用户确认？

### 决策点 7：数据迁移策略

- **自动迁移（旧 localStorage → 新 Schema）**：收益：用户无感知、进度不丢；风险：迁移脚本有 bug 可能损坏数据（但可先做只读备份）。
- **手动迁移（用户导出旧数据再导入）**：收益：最可控；风险：用户操作门槛高、体验差。
- **建议：自动迁移 + 备份旧数据**。用户确认？
