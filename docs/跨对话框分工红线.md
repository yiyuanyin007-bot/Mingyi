# 跨对话框分工红线

> **版本**：V1  
> **适用范围**：方剂卡片对话、操作系统对话、以及未来新增的任何功能对话  
> **核心原则**：数据内容 vs 前端交互 明确分离，灰色地带显式协商

---

## 一、红线总览

```
┌─────────────────────────────────────────────────────────┐
│  用户（陈医生）                                          │
│      │                                                  │
│      ├──────────→ 提出需求（如"点击药名要显示类方"）    │
│      │                                                  │
│      ├──────────→ 方剂卡片对话（数据结构 + 内容）        │
│      │                    │                            │
│      │                    ↓                            │
│      │              输出：JSON Schema                   │
│      │                    │                            │
│      │                    ↓                            │
│      ├──────────→ 操作系统对话（前端渲染 + 交互）        │
│      │                    │                            │
│      │                    ↓                            │
│      │              输出：HTML/CSS/JS                    │
│      │                    │                            │
│      └──────────→ 用户测试反馈                           │
│                           │                            │
│                           ↓                            │
│              问题归属：数据层 → 方剂卡片                  │
│              问题归属：交互层 → 操作系统                  │
│              问题归属：灰色地带 → 双方协商                │
└─────────────────────────────────────────────────────────┘
```

## 二、方剂卡片对话（本对话）的职责

### 2.1 数据内容（100% 负责）

| 任务 | 说明 | 输出格式 |
|------|------|---------|
| **卡片 Schema 设计** | `formula_card` / `source_card` / `experience_card` 的字段定义 | JSON Schema 文档 |
| **卡片数据生成** | 从原始资料提取、清洗、结构化，注入 `data/*.json` | `data/formula_cards.json` 等 |
| **处方解析** | 从医案/条文文本中提取药名+剂量，输出结构化数组 | `prescription_structured: [{name, dose}]` |
| **药名别名映射** | 生甘草→甘草、赤芍→芍药、红枣→大枣 等映射关系 | `data/herb_alias_map.json` |
| **类方分组数据** | 每味药出现在哪些方中，按 lineage 分组 | `data/herb_alias_map.json` 中的 `herb_class_map` |
| **内容质量** | 摘要长度、标签准确性、症状提取完整性 | 人工审核 + 脚本检查 |
| **数据来源追溯** | 每条内容的原始文件路径、URL、作者、日期 | `local_path`, `url`, `source` 字段 |

### 2.2 数据验证（100% 负责）

- [ ] JSON 合法性：`json.load()` 通过，无语法错误
- [ ] Schema 完整性：必填字段不缺失，字段类型正确
- [ ] 覆盖度检查：目标方清单 vs 实际卡片，输出缺口报告
- [ ] 数据备份：修改前复制到 `data/archive/`

### 2.3 不做的（明确排除）

- ❌ 不写 CSS 样式
- ❌ 不写 HTML 结构
- ❌ 不写 JS 事件处理（onclick、弹窗、跳转）
- ❌ 不决定前端加载策略（fetch vs script src vs 硬编码）
- ❌ 不处理浏览器兼容性问题
- ❌ 不处理移动端适配

## 三、操作系统对话的职责

### 3.1 前端交互（100% 负责）

| 任务 | 说明 | 输出格式 |
|------|------|---------|
| **页面渲染** | 学习页、考试页、卡片列表、统计页的 HTML 结构 | `app/index.html` |
| **CSS 样式** | 所有视觉呈现：颜色、字体、间距、圆角、边框、主题切换 | `<style>` 内联或外部 CSS |
| **点击交互** | 药名点击、方剂点击、按钮点击、选项选择、提交判分 | JS 事件处理函数 |
| **弹窗管理** | 弹窗打开/关闭、遮罩、ESC 关闭、点击外部关闭 | `showModal()` / `closeModal()` |
| **页面跳转** | 学习页↔卡片列表、考试↔结果、弹窗内跳转 | `goToLearn()` / `goToDashboard()` |
| **状态管理** | 当前页面、活动卡片、考试状态、主题模式 | `state` 对象 |
| **痕迹记录 UI** | "今日学习"按钮、学习报告弹窗、导出按钮、查看次数显示 | 可见的 UI 元素 |
| **localStorage 持久化** | 进度保存、进度读取、导出/导入 JSON | `localStorage` 操作 |

### 3.2 前端验证（100% 负责）

- [ ] 语法检查：JS 括号/引号平衡，无语法错误
- [ ] 功能测试：点击有响应、弹窗显示、跳转成功、选项不重复
- [ ] 视觉测试：dark/light 主题切换、移动端适配、弹窗不遮挡
- [ ] 性能测试：35 张卡片加载不慢、弹窗不卡顿

### 3.3 不做的（明确排除）

- ❌ 不从原始资料提取内容（如从黄煌医案中提取处方）
- ❌ 不定义卡片 Schema（字段名、字段类型由方剂卡片对话决定）
- ❌ 不生成 `data/*.json` 文件
- ❌ 不验证 JSON 数据内容准确性（如剂量是否正确）

## 四、灰色地带（需双方协商）

以下任务涉及两方协作，必须在动手前显式确认分工：

### 4.1 药名别名加载策略（当前焦点）

| 方案 | 数据层负责 | 交互层负责 | 协商点 |
|------|----------|----------|--------|
| A. 硬编码在 JS | 提供映射表内容 | 写入 `index.html` JS | 内容更新时谁同步？ |
| B. `<script src="herb-aliases.js">` | 提供 JSON 真相源 + 生成脚本 | 在 HTML 中引入 `<script src>` | 生成脚本放在哪？何时运行？ |
| C. 构建工具注入 | 提供 JSON | 配置 Vite/Webpack 注入 | 是否引入构建工具？ |
| D. 检测 file:// 双路径 | 提供 JSON | 写 fallback 逻辑 | 代码复杂度谁承担？ |

**当前共识**：方案 B（`<script src>`）。方剂卡片对话提供 `data/herb_alias_map.json` 和生成脚本，操作系统对话在 `index.html` 中引入 `<script src="herb-aliases.js">`。

### 4.2 数据格式变更

- 方剂卡片对话新增字段（如 `prescription_structured`）→ **必须先通知操作系统对话**，确认前端能否渲染
- 操作系统对话需要新字段（如 `herb_click_count`）→ **必须先通知方剂卡片对话**，确认数据层能否提供

**协商机制**：任何 Schema 变更，先更新 `docs/视觉设计规范-V1.md` 或新建 `docs/接口变更通知.md`，另一方确认后再实施。

### 4.3 验证依赖

- 数据层验证（JSON 合法）通过后，**不保证**交互层能正确渲染
- 交互层验证（点击有响应）通过后，**不保证**数据内容准确
- 双方各自验证，最终由用户端到端测试确认

### 4.4 mobile.html 同步

- 当前 `index.html` 已大幅更新，但 `mobile.html` 落后
- 是否合并为响应式一套代码？→ 操作系统对话决定技术方案，但需告知方剂卡片对话（可能影响数据加载方式）

### 4.5 部署上线

- 部署后 file:// 问题消失，加载策略可以简化
- 但部署环境（GitHub Pages / Netlify / Vercel）由操作系统对话选择
- 部署后数据层是否需要调整（如 API 路径）→ 需协商

## 五、接口契约（双方必须遵守）

### 5.1 数据层 → 交互层 的数据契约

```javascript
// 方剂卡片对话保证以下数据格式：

// 1. formula_cards.json 中每张卡片必须有：
{
  "id": "string",
  "formula_name": "string",
  "name": "string", // 显示名
  "data": {
    "canonical": {
      "herbs": [{"name": "string", "dosage": "string"}]
    }
  },
  "references": {
    "clinical_cases": [{
      "title": "string",
      "summary": "string",
      "prescription_structured": [{"name": "string", "dose": "string"}], // 可选，但有则必须合规
      "tags": ["string"]
    }],
    "teacher_notes": [{"title": "string", "summary": "string"}]
  }
}

// 2. herb_alias_map.json 中必须有：
{
  "alias_to_standard": {"赤芍": "芍药", "生甘草": "甘草", ...},
  "herb_class_map": {"芍药": {"class_name": "柴胡剂/桂枝剂", "count": 8}, ...}
}

// 3. 所有药名必须使用标准名（如"芍药"而不是"赤芍"），别名通过映射表转换
```

### 5.2 交互层 → 数据层 的需求契约

```javascript
// 操作系统对话保证以下接口存在：

// 1. 页面加载后，window.HERB_ALIAS_MAP 必须可用（无论是 fetch、script src 还是硬编码）
// 2. 弹窗内跳转必须使用 handleModalGoToLearn(id)，不能直接用 goToLearn()
// 3. 所有新增 CSS 类必须使用 CSS 变量（--bg-panel, --border, --accent 等）
// 4. 任何 Schema 变更前，先通知方剂卡片对话确认
```

## 六、问题归属速查表

| 用户反馈 | 归属 | 处理方 |
|---------|------|--------|
| "点击药名弹窗显示空" | 数据层（别名映射没加载）或 交互层（弹窗没渲染） | 先查 `window.HERB_ALIAS_MAP` 是否存在 → 数据层；存在但渲染空 → 交互层 |
| "药名没加粗" | 交互层（CSS 没应用 `.rx-herb-name`） | 操作系统对话 |
| "剂量显示不对" | 数据层（提取错误）或 交互层（渲染错误） | 先查 `prescription_structured` 数据 → 数据层；数据对但显示错 → 交互层 |
| "跳转没反应" | 交互层（跳转函数冲突） | 操作系统对话 |
| "内容重复/不相关" | 数据层（摘要提取错误） | 方剂卡片对话 |
| "页面太挤/太散" | 交互层（布局/CSS） | 操作系统对话 |
| "刷新后进度丢失" | 交互层（localStorage 没存） | 操作系统对话 |
| "卡片数量不够" | 数据层（卡片没生成） | 方剂卡片对话 |
| "考试选项重复" | 交互层（generateOptions 逻辑） | 操作系统对话 |
| "条文编号不对" | 数据层（source_cards 字段错误） | 方剂卡片对话 |

## 七、变更流程

任何涉及两方的事务，按以下流程：

```
1. 提出方写《接口变更通知.md》（或在本文档注释区记录）
   └─ 变更内容、原因、影响范围、建议方案
2. 另一方在 1 个回合内确认或提出异议
3. 双方确认后，各自在自己的职责范围内实施
4. 实施完成后，提出方验证端到端是否可用
5. 可用 → 更新本文档的"当前共识"部分
   不可用 → 回到步骤 1 重新协商
```
