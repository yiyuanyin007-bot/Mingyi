## 二、关键决策与决策逻辑

### 2.1 为什么最终采用“来源感知”的 v2 清洗？

- **决策**：放弃“一刀切”的 v1，改为根据文件类型选择清洗策略。
- **逻辑**：
  - 倪海厦 txt 的排版特征是“几乎每行后都有一个空行”，空行不是段落分隔，而是扫描版式残留。v1 按“空行分段”导致句子被切成碎片；v2 采用“删除所有空行、合并所有非空行”，使文本恢复成连续段落。
  - CHM/HTML 文件中存在残缺标签（如 `<a href="...` 未闭合）、HTML 属性残留（`tle="...">`、`bordercolor="#FFFFFF">`）、导航字符串。v2 增加了对未闭合标签、属性片段、内联导航的清除规则。
- **量化结果**：v2 平均行长度从 v1 的 69.6 提升到 148.1，HTML/导航残留从 3 处降到 0。

### 2.2 为什么把 10 张卡片追加到现有 v8 MVP，而不是新建页面？

- **决策**：在 `app/shanghanlun-v8-mvp.html` 的 `CARDS` 数组中追加 5 张新卡片，使总数达到 10 张。
- **逻辑**：
  - 已有原型已具备学习视图、考试视图、统计视图，复用成本最低。
  - 新建页面需要重新对接样式和 JS，时间收益不高。
  - 先备份（`app/archive/shanghanlun-v8-mvp-before-10cards.html`），再修改，可回滚。

### 2.3 为什么用浏览器自动化（WebBridge）而不是静态抓取来调研知乎/百度？

- **决策**：启动 Kimi WebBridge，用真实浏览器打开知乎专栏、百度健康、百度百家号并提取正文。
- **逻辑**：
  - `FetchURL` 对知乎返回 403，说明需要浏览器环境或登录态。
  - 百度健康/百家号内容依赖 JS 渲染，静态抓取容易拿到不完整的骨架或重定向页。
  - WebBridge 能使用用户真实会话，且能截图验证页面确实加载成功。

### 2.4 为什么最终认定“严格匹配太阳病”是错误策略？

- **决策**：在对比报告中明确指出，下一步应同时匹配“太阳病 / 太阳中风 / 太阳伤寒 / 伤寒（在太阳病语境下）”。
- **逻辑**：
  - 大青龙汤条文原文为“太阳中风，脉浮紧……”，小青龙汤条文为“伤寒，表不解……”，麻黄杏仁甘草石膏汤条文为“发汗后……”，均无“太阳病”三字。
  - 仅匹配“太阳病”会漏掉太阳病篇中大量以“太阳中风”“伤寒”开头的核心方证。
  - 知乎专栏和中医资源网都把这些方剂归入太阳病类方，说明它们在学理上属于同一范畴。

## 三、犯的错误与走的弯路

### 3.1 Markdown 抽样解析被 `\r\n` 击败

- **现象**：读取 `extracted/sample_segments_raw.md` 时，按 `\n\n` 切分和正则 `r'## 片段 \d+'` 都失效，无法定位片段。
- **根因**：Windows 下文件实际保存为 `\r\n`，而脚本按 `\n` 处理；同时正则对混合编码环境不稳定。
- **修复**：读取后先 `text.replace('\r\n', '\n')`，再用字符串查找 `## 片段` 定位块边界，而不是依赖正则匹配标题行。
- **经验**：在 Windows 处理中文 Markdown，永远先做换行符统一；能用字符串查找的地方，不要过度依赖正则。

### 3.2 v1 清洗“保留空行”反而破坏了倪海厦 txt

- **现象**：v1 清洗后的倪海厦片段仍然一行一行断开，每行后都有空行，无法阅读。
- **根因**：误以为空行是段落分隔；实际上倪海厦 txt 中“空行”是版式残留，真正的分隔是“条文编号”。
- **修复**：v2 对倪海厦 txt 删除所有空行，合并所有非空行，再按条文编号重分。
- **经验**：清洗策略必须“来源感知”，不能假设所有文本的空行都有相同语义。

### 3.3 WebBridge 截图路径被 URL 编码反噬

- **现象**：调用 `screenshot` 时传入 `path: "C:/Users/Chen/Desktop/经方学习系统（旧版）/app/xxx.png"`，返回成功但文件找不到；后来发现第一次被写到了 `C:\Users\Chen\Desktop\%E7%BB%8F...` 这种带百分号的目录里。
- **根因**：请求体中的路径被当作字面量处理，中文字符被 URL 编码后未被 daemon 解码。
- **修复**：后续传路径时用中文直写，且用 `Get-ChildItem -Recurse` 搜索确认文件位置。
- **经验**：与 WebBridge 交互时，路径尽量用 ASCII 或确认 daemon 的解码行为；截图后立刻在磁盘搜索验证。

### 3.4 卡片注入时把 `CARDS` 数组包成了二维数组

- **现象**：修改后的原型页面卡片列表为空，`evaluate` 显示 `CARDS.length === 1`。
- **根因**：脚本写成 `const CARDS = [` + json.dumps(list) + `];`，而 `json.dumps(list)` 本身已带 `[]`，导致外层又多一层 `[ ... ]`。
- **修复**：改为 `const CARDS = ` + json.dumps(list) + `;`，让 `json.dumps` 的外层括号直接作为 `CARDS` 的数组括号。
- **经验**：替换内嵌 JSON 时，要先看清原文件是 `const X = [ ... ]` 还是 `const X = ...`；序列化后务必用 `JSON.parse` 或浏览器 `evaluate` 验证。

### 3.5 误把 `raw_倪海厦伤寒论_extracted.md` 当垃圾跳过

- **现象**：太阳病.md 缺少五苓散、大青龙汤、小青龙汤等核心条文。
- **根因**：脚本中把文件名匹配 `raw_.*_extracted\.md$` 的文件跳过，认为它们是“自动生成的目录/索引”。但该文件有 1.5 MB，包含大量方剂与条文，是极具价值的补充源。
- **修复方向**（尚未实施）：在报告中建议把它从“跳过名单”中移除，或作为专门的“条文补全源”。
- **经验**：跳过规则不能只看文件名是否像“生成文件”，要结合文件大小和内容抽样判断价值；清洗规则应和数据价值规则解耦。

### 3.6 用 PowerShell 输出判断中文字符导致误判

- **现象**：多次 Shell 命令返回中文乱码，无法确认结果是否正确，甚至一度怀疑数据本身损坏。
- **根因**：PowerShell 默认代码页与 UTF-8 不一致，Python 打印的 UTF-8 字符串被错误解码显示。
- **修复**：不再依赖 Shell 回显判断中文内容，而是把结果写入文件后使用 `ReadFile` 读取。
- **经验**：在 Windows PowerShell 中处理中文，永远以文件内容为准，不要信任终端回显。

## 四、得到验证的有效改进

### 4.1 来源感知清洗显著提升质量

- 倪海厦 txt：删除所有空行后合并，平均行长度提升 10 倍以上。
- CHM HTML：增加了对未闭合 `<a ...`、属性残留、内联导航的清洗，HTML 残留从 3 降到 0。

### 4.2 质量过滤剔除目录噪声

- 在生成 `extracted/太阳病.md` 时加入：
  - 中文占比 ≥ 40%
  - 长度 10–500 个汉字
  - 数字占比 ≤ 20%
  - 点号不过量
- 有效过滤了“辨太阳病脉证并治法上 9 辨太阳病脉证并 41 .”这类目录碎片。

### 4.3 全局去重避免同一条文重复

- 以“仅保留汉字”为 key 对跨来源条文去重，使 247 次原始命中收敛为 198 条。
- 许叔微《伤寒九十论》的全部条文与《伤寒悬解》重复，去重后该章节为空，验证了跨来源重复的严重性。

### 4.4 原型卡片结构化便于训练

- 把卡片字段统一为 `source_text`、`symptom_profile`（necessary/common/excluding）、`pathology`、`herbs`、`usage`、`contraindications`，使考试视图可以自动生成“方名→症状”“症状→方名”等题型。

### 4.5 用脚本量化覆盖度

- `scripts/check_coverage.py` 自动输出“目标方剂 → 是否出现在太阳病.md”，快速发现大青龙汤、小青龙汤、麻杏甘石汤等缺口。
- 比手动翻阅更高效，也更有说服力。

## 五、仍未解决的问题与风险

### 5.1 太阳病.md 覆盖度不足

- 严格匹配“太阳病”导致太阳中风、伤寒开头的条文大量丢失。
- 五苓散、大青龙汤、小青龙汤、栀子系列、柴胡类变证缺失或只有旁注。

### 5.2 卡片只有 10 张，样本量小

- 10 张卡片不足以支撑“太阳病类方”训练，且混入大承气汤这种阳明病方。
- 建议至少扩展到 20–25 张，并按桂枝类/麻黄类/葛根类/柴胡类/栀子类/水血证类分组。

### 5.3 缺少病机与现代应用层

- 目前卡片只有原文、症状谱、药物、禁忌，缺少知乎式的病机串讲和百度健康式的现代对应。
- 这会影响初学者“为什么用这个方”的理解深度。

### 5.4 临床医案层尚未接入

- `clinical/` 目录有临床资料，但尚未与卡片做 `experience_card` 关联。
- 后续需要把“条文 → 方剂 → 医案”三线打通。

### 5.5 外部来源质量不可控

- 百度健康/百度知道中存在中西医概念混淆（如把太阳伤寒当成伤寒杆菌传染病）。
- 未来需要给外部来源打分或分级，避免低质量内容进入卡片。

## 六、沉淀下来的工作范式

1. **清洗原则要先抽样、再赛马、再落地**
   - 抽 200–300 字片段 → 设计一版原则 → 洗完看效果 → 再设计第二版 → 对比 → 出报告。
   - 不要一次性写完整规则，避免在未知数据上过度设计。

2. **所有中文输出先写文件，再 `ReadFile` 确认**
   - Windows PowerShell 终端回显不可信，文件内容才是真相。

3. **修改内嵌 JSON/HTML 前先备份，修改后立刻验证**
   - 备份到 `archive/`，修改后用 Python `json.loads` 或浏览器 `evaluate` 验证。

4. **网络调研优先用搜索工具定位，再用浏览器自动化提取**
   - `SearchWeb` 快速找 URL，WebBridge 解决登录/JS 渲染/反爬。

5. **对比报告要有量化表**
   - “我们觉得缺”不够，要列出“目标方剂 → 是否出现”的覆盖表，才能清晰定位缺口。

6. **来源追溯字段不能丢**
   - 每条语句、每张卡片都要保留原始路径，方便回查和版本更新。

## 九、外部检索策略：多样化、可迭代、可对比

### 9.1 总体原则

外部检索不是“搜一次就结束”，而是一个**四轮递进**的过程：

1. **广撒网**：用通用关键词把主要信息源扫一遍，建立全貌。
2. **补缺口**：根据内部覆盖度检查（如 `coverage_check.md`）列出缺失项，定向检索。
3. **追权威**：针对核心条文、剂量、煎服法，回到古籍或权威注家原文核对。
4. **验长尾**：对争议点、现代应用、禁忌等，用多渠道交叉验证。

### 9.2 检索渠道矩阵（按本项目实际可用源）

| 渠道 | 代表站点 | 优势 | 劣势 | 适用阶段 | 典型反爬/限制 |
|---|---|---|---|---|---|
| **专业中医站点** | 中医资源网、伤寒论相关古籍库 | 条文完整、出处清晰、权威性强 | 页面老旧、可能 404、广告多 | 追权威、补条文 | 部分站点有简单反爬 |
| **知乎专栏/回答** | 知乎 | 病机串讲、类方对比、现代案例丰富 | 质量参差、需甄别作者资质 | 广撒网、验长尾 | 静态抓取 403，需 WebBridge |
| **百度健康/百科/知道** | 百度系 | 现代病症对应、剂量/禁忌列表化 | 中西医概念混淆、内容商业化 | 广撒网、补现代应用 | JS 渲染，需浏览器 |
| **搜索引擎结果页** | 百度/必应 | 快速发现新站点 | 只给标题摘要，正文需二次抓取 | 发现 URL、评估热度 | 无 |
| **本地资料** | `raw/`、`clinical/`、`extracted/` | 可控、可版本化、与卡片直接对接 | 覆盖度依赖清洗与提取质量 | 全程 | 无 |

### 9.3 检索词设计模板

同一主题至少准备三组词，覆盖不同颗粒度：

| 目标 | 通用型 | 条文型 | 对比型 | 现代应用型 |
|---|---|---|---|---|
| 太阳病类方 | `太阳病 常用方` | `太阳病 条文 主之` | `麻黄汤 桂枝汤 区别` | `太阳病 现代 感冒 流感` |
| 大青龙汤 | `大青龙汤 太阳病` | `太阳中风 脉浮紧 大青龙汤主之` | `大青龙汤 麻黄汤 比较` | `大青龙汤 高热 无汗` |
| 柴胡类变证 | `小柴胡汤 变证` | `伤寒五六日 中风 柴胡汤证具` | `小柴胡汤 大柴胡汤 区别` | `小柴胡汤 往来寒热 现代` |

经验：**“条文型”查询最容易命中权威来源；“对比型”查询最容易获得高质量知乎专栏；“现代应用型”查询最容易在百度健康找到对应病症。**

### 9.4 四轮检索流程示例（以大青龙汤缺失为例）

**Round 1：广撒网**
- 搜索：`太阳病 类方 大青龙汤 小青龙汤`
- 收集 5–10 个 URL，快速判断哪些站点有完整条文。

**Round 2：补缺口**
- 发现 `太阳病.md` 缺少大青龙汤原文。
- 定向搜索：`太阳中风 脉浮紧 大青龙汤主之`
- 在中医资源网或古籍库抓取原文段落。

**Round 3：追权威**
- 回到《伤寒论》原文/宋本/成无己《注解伤寒论》核对条文。
- 若本地 `raw/classical/` 有 PDF/CHM，优先解析本地权威源。

**Round 4：验长尾**
- 知乎搜索：`大青龙汤 为什么 无汗 烦躁`
- 百度健康搜索：`大青龙汤 禁忌`
- 交叉验证：是否都提到“汗出多、热退即停服”“表虚有汗者禁用”。

### 9.5 检索策略对比评估表

每次外部检索后，应对本轮策略做一个简短评估，写入 `extracted/search_strategy_report.md`：

| 评估维度 | 权重 | 说明 | 评分（1–5） |
|---|---|---|---|
| **召回率** | 30% | 目标信息中有多少被找到 |  |
| **准确率** | 25% | 找到的内容有多少可用 |  |
| **权威性** | 20% | 来源是否古籍/权威注家/专业平台 |  |
| **可提取性** | 15% | 正文是否容易被清洗/结构化 |  |
| **访问成本** | 10% | 是否需要登录、浏览器、多次重试 |  |

**示例（知乎专栏 vs 百度健康）**

| 维度 | 知乎专栏 | 百度健康 |
|---|---|---|
| 召回率 | 4（类方、病机覆盖广） | 3（现代对应病症多，古条文少） |
| 准确率 | 3（需甄别作者） | 2（常见中西医概念混淆） |
| 权威性 | 2（个人作者） | 2（平台内容，来源不透明） |
| 可提取性 | 4（文章结构清晰） | 3（JS 渲染，需浏览器） |
| 访问成本 | 3（需 WebBridge 防 403） | 3（需 WebBridge） |
| **加权总分** | **3.35** | **2.50** |

> 结论：知乎专栏更适合补“病机串讲、类方对比”，百度健康更适合补“现代病症对应、禁忌条目”；核心条文仍应以本地古籍/专业中医站点为准。

## 十、标准化、可迭代的 quality assessment 方案

### 10.1 评估对象与层级

| 层级 | 对象 | 示例 | 评估周期 |
|---|---|---|---|
| L0 数据源 | 原始文件/网页 | `raw/倪海厦伤寒论.txt`、知乎专栏 | 每次新增源 |
| L1 清洗文本 | 清洗后的段落 | `extracted/太阳病.md` 中的条目 | 每次清洗迭代 |
| L2 候选卡片 | `formula_card` / `source_card` | `app/shanghanlun-v8-mvp.html` 中的卡片 | 每次提取/审核 |
| L3 卡组/产品 | 一组卡片 + 考试/统计 | 太阳病类方卡组 | 每次发版 |

### 10.2 标准化评分量表（0–5 分）

统一使用 **5 分制**，每个维度给出明确的 0/1/3/5 标准，减少主观性：

| 维度 | 权重 | 5 分标准 | 3 分标准 | 1 分标准 | 0 分标准 |
|---|---|---|---|---|---|
| **来源权威性** | 20% | 古籍/权威注家/知名中医院校 | 专业中医平台/有出处的专栏 | 个人博客/问答社区 | 来源不明/营销号 |
| **内容准确性** | 25% | 与《伤寒论》原文一致，剂量煎服法无误 | 整体正确，仅个别细节有出入 | 有明显中西医概念混淆 | 事实错误 |
| **结构完整性** | 20% | 含原文、症状谱、病机、方药、煎服、禁忌 | 含原文+症状+方药 | 仅有片段或单一维度 | 无法构成卡片 |
| **与项目目标一致性** | 15% | 直接服务于太阳病类方学习目标 | 相关但偏离核心目标 | 仅边缘相关 | 无关 |
| **可验证性** | 10% | 可追溯到具体条文/页码/URL | 可追溯到站点但无精确锚点 | 仅有作者断言 | 无法验证 |
| **现代可用性** | 10% | 有病机串讲或现代病症对应 | 有简单现代解释 | 无现代解释 | 纯古文且难以理解 |

**总分计算公式**

```
score = Σ(维度得分 / 5 × 权重) × 100
```

**分级阈值**

| 总分 | 等级 | 处理动作 |
|---|---|---|
| ≥ 85 | A（可直接采用） | 批准入库 |
| 70–84 | B（需小修） | 批准但记录待改进项 |
| 55–69 | C（需大修） | 退回补全或人工重写 |
| < 55 | D（拒绝） | 拒绝并记录原因 |

### 10.3 卡片级 QA 检查清单

每张候选卡片在批准前必须过以下清单：

- [ ] `source_text` 能追溯到具体条文或来源段落。
- [ ] `formula_name` 与条文中的方名一致。
- [ ] `symptom_profile.necessary` 无漏项，`excluding` 无反向错误。
- [ ] `herbs` 剂量与煎服法来自同一来源，单位统一。
- [ ] `contraindications` 至少有一条明确禁忌或“慎用”提示。
- [ ] 非太阳病方不混入太阳病卡组（如大承气汤阳明病方需剔除或单独标记）。
- [ ] 卡片 `canonical` 字段已标记权威来源优先级。

### 10.4 可迭代的评估工作流

建议把质量评估做成一个闭环：

```
1. 自动初评：脚本/规则按量表给候选打分 → 输出 candidate_scores.json
2. 人工复核：审核员抽检 20% 或全部 B/C 级 → 写入 reviewer_note
3. 修正迭代：对 C/D 级退回补全，重新跑评估
4. 批准入库：A/B 级进入 CARDS 数组或 extracted/ 文档
5. 使用反馈：考试错误率、用户掌握度低的卡片自动回到待审核池
6. 周期复盘：每批卡片生成后，统计平均分、拒绝率、常见扣分项
```

### 10.5 过程指标看板

每次迭代应记录以下指标，形成可对比的趋势：

| 指标 | 说明 | 本次数值（参考） |
|---|---|---|
| 清洗后可用率 | 清洗后可用于提取的段落 / 原始命中段落 | 198 / 247 ≈ 80.2% |
| 覆盖率 | 目标方剂在文档/卡片中出现比例 | 10 / 36 ≈ 27.8% |
| 去重率 | 被去重的重复段落 / 原始命中段落 | 49 / 247 ≈ 19.8% |
| 卡片平均分 | 按 L2 量表评估的候选卡片平均分 | 待评估 |
| A 级率 | A 级卡片 / 总候选卡片 | 待评估 |
| 拒绝率 | D 级 + C 级退回 / 总候选 | 待评估 |

### 10.6 输出模板

每次质量评估应生成一个 Markdown 报告，建议路径：

- `extracted/quality_report_YYYYMMDD.md`
- `extracted/search_strategy_report_YYYYMMDD.md`

报告至少包含：

1. 本次评估范围与目标
2. 评分量表与阈值
3. 各维度平均分与短板
4. 具体问题清单（来源、行号、问题描述、建议修复）
5. 与上轮评估的对比

### 12.2 提取方法

1. **WebBridge 打开老师主页并滚动到底**，触发瀑布流加载。
2. **网络抓包**捕获小红书 `edith.xiaohongshu.com/api/sns/web/v1/user_posted` 请求。
3. **解析 API 响应**，得到 `note_id`、`display_title`、`xsec_token`、`cover_url`。
4. **批量下载封面图**：238 张全部成功。
5. **OCR 识别**：在项目根目录新建隔离虚拟环境 `venv_ocr`，安装 `rapidocr_onnxruntime`，对 238 张图做中文 OCR。
6. **清洗合并**：去掉封面标题行、合并断行、按条文编号排序，生成 `伤寒论条文_小红书针道轩.md`。

### 12.3 关键弯路

- **直接打开笔记详情页 404**：`https://www.xiaohongshu.com/explore/{note_id}` 会提示“当前笔记暂时无法浏览”。必须附带 `xsec_token` 才能访问，而 `xsec_token` 只在 API 响应或主页链接里。
- **不要用浏览器 `fetch` 直接调 API**：小红书 API 需要签名/反爬头，手动 `fetch` 返回 `{"code":-1}`。但浏览器自己发出的请求（抓包）可以正常拿到响应。
- **OCR 不能在主会话里跑完**：238 张图 × ~5 秒 ≈ 20 分钟，超过前台 300 秒限制，改为 Background Task（3600 秒）才完成。
- **封面图本身就是内容**：老师把每条《伤寒论》条文做成一张图，OCR 后可直接作为 `source_text` 候选源。

### 12.4 数据质量

## 十九、修复选择题选项重复问题（2026-06-14）

### 19.1 现象

用户反馈：考试中有时会出现两个一模一样的选项。

### 19.2 根因

`app/index.html` 的 `generateOptions(cardId, type)` 原来从其他卡片随机取 3 张作为干扰项，再与正确答案一起排序。当不同卡片的正确答案在某种题型下标签相同时（例如多张方的第一味药都是「桂枝」，或多张方的煎服法文本相同），就会出现重复选项。

### 19.3 修复

重写 `generateOptions`：

1. 先计算并加入正确答案选项。
2. 用 `Set` 记录已用标签。
3. 遍历随机打乱的其余卡片，只挑选标签未出现过的干扰项，直到凑齐 4 个选项。
4. 若题库过小凑不齐 4 个，才用占位符兜底（当前 35 张卡片不会触发）。

### 19.4 验证

- WebBridge 打开 `http://localhost:8000/app/index.html?v=4`。
- 对前 10 张卡片的 6 种题型各调用一次 `generateOptions`。
- 结果：`dupCount=0`，所有选项标签唯一。

## 二十、核心药物组合升级与练习/考试模式拆分（2026-06-14）

### 20.1 背景

在 35 张卡片、6 向量、选项去重已完成后，用户提出三个新需求：

1. 把「方名→药物」从单味首药升级为核心药物组合。
2. 区分「练习」（即时反馈）与「考试」（提交后统一判分）。
3. 增加学习页交互：剂量/病机/禁忌/煎服法可点击显示，参考资料可点击外链。

### 20.2 关键决策

#### 决策 1：用独立研究文件 `core_herbs_research.json` 保存核心组合

- **做法**：新增 `data/core_herbs_research.json`，每张卡片记录 `core_herbs`、`core_combinations`、`core_rationale`、`core_sources`、`source_urls`。
- **理由**：
  - 把「研究资料」与「卡片真相源」解耦，方便后续换来源或补来源。
  - `source_urls` 等字段不适合全部塞进 `formula_cards.json` 的 canonical，但可以通过脚本注入。
- **结果**：`formula_cards.json` 只保留出题必需字段，研究文件保留完整 rationale 与链接。

#### 决策 2：核心组合 ≠ 首药，而是药对/药组

- **做法**：
  - 桂枝汤：桂枝 + 芍药
  - 麻黄汤：麻黄 + 桂枝 + 杏仁
  - 小青龙汤：麻黄 + 桂枝 + 干姜 + 细辛 + 五味子
  - 大承气汤：大黄 + 芒硝 + 厚朴 + 枳实
- **理由**：临床记忆和辨证抓手通常是药对/药组，单味首药太容易靠猜。
- **经验**：出题时选项也必须是组合，否则去重后仍可能出现「桂枝」同时作为多个方的首药。

#### 决策 3：练习与考试共享同一视图，靠 `state.exam.mode` 分支

- **做法**：
  - `practice-card`：即时反馈，答完才能下一题。
  - `practice-similar`：类方混合练习。
  - `exam`：随机抽题，选择只记录不判分，提交后统一出结果。
  - `daily`：保持原有每日复习逻辑。
- **理由**：减少新页面成本，用户在同一套交互里切换模式。
- **代价**：`renderExam`、`selectOption`、`renderExamNav` 里多了分支判断，代码复杂度上升。
- **经验**：当同一页面承载多种模式时，先把状态机画清楚（mode/submitted/finished 的组合），再写代码。

#### 决策 4：考试答案预填充，避免数组长度不一致

- **做法**：`startExamMode` 生成题目后，立即创建 `state.exam.answers = questions.map(q => ({ question: q, selected: null, isCorrect: null }))`。
- **理由**：
  - 用户可来回切换题目，选择可随时修改。
  - 提交时遍历固定长度的数组，避免 `push` 模式在跨题导航时错位。
- **经验**：「先占位后填充」比「边答题边 push」更适合需要回顾/修改的场景。

#### 决策 5：掌握度更新按 `question.cardId` 而不是 `state.activeCardId`

- **做法**：修改 `updateMasteryAfterAnswer(vector, isCorrect, cardId)`，调用时传入题目所属卡片 ID。
- **理由**：
  - 每日复习和模拟考试都会跨卡片抽题。
  - 原实现始终用 `state.activeCardId`，导致非当前活动卡片的答题记录被记到错误卡片上。
- **经验**：任何涉及「当前活动对象」的状态更新，在跨对象抽题场景下都要显式传入对象 ID。

### 20.3 走的弯路

#### 弯路 1：考试模式下一题按钮一开始对未答题禁用

- **现象**：用户希望在考试中能自由回看上一题，但原设计下一题必须答完才启用。
- **修复**：考试模式下「上一题」始终可用，「下一题/提交试卷」始终可用；未提交前不强制答题。
- **经验**：练习模式要「逼用户先答」，考试模式要「允许浏览全卷」，两种模式的心理模型不同。

#### 弯路 2：练习模式下返回上一题会重复计分

- **现象**：原 `selectOption` 只要 `state.exam.finished` 为 false 就 push 答案并更新统计。用户返回上一题再点选项，会重复 push。
- **修复**：返回已答题时 `state.exam.finished` 为 true，`selectOption` 直接 return；`applyAnswerUI` 只负责渲染，不再改状态。
- **经验**：统计类操作一定要幂等，或至少用「已作答」状态 guarding。

#### 弯路 3：参考资料链接注入脚本临时创建后没留档

- **现象**：用一次性脚本 `inject_links.py` 把 `source_urls` 写进 `formula_cards.json`，脚本运行后即删除。
- **风险**：后续若需批量更新链接，没有可复现脚本。
- **修复/建议**：这种「一次性数据迁移」脚本应保留在 `scripts/` 下，例如 `scripts/inject_core_source_urls.py`。

#### 弯路 4：浏览器缓存导致 WebBridge 测试看到旧版本

- **现象**：修改 `index.html` 后，WebBridge 仍加载旧页面，测试结果和代码不符。
- **修复**：测试前执行 `location.reload(true)` 强制刷新。
- **经验**：本地开发也要做缓存戳；每次大改后测试，先强制刷新。

### 20.4 可复用的工程模式

1. **数据与研究分离**
   - 把「研究/来源」放在独立 JSON，通过脚本注入到真相源。
   - 适用场景：卡片需要来源、rationale、外链，但核心 Schema 不想膨胀。

2. **状态机驱动同一视图的多模式**
   - `state.exam.mode` + `state.exam.submitted` + `state.exam.finished` 三元组控制练习/考试行为。
   - 适用场景：考试、练习、每日复习共享一套 UI，但交互节奏不同。

3. **答案预填充 + 统一提交**
   - 先创建占位对象，用户选择只改字段，提交时一次性判分。
   - 适用场景：需要回顾、修改、批量判分的测试。

4. **按题目标识更新掌握度**
   - 把 `cardId` 从题目对象传入更新函数，而不是依赖全局 active state。
   - 适用场景：任何跨对象抽题/复习系统。

5. **WebBridge 截图验证 UI**
   - 颜色、布局类改动，用 WebBridge `screenshot` 截图后肉眼确认，比 accessibility tree 更直观。
   - 适用场景：UI 反馈、响应式、主题色调整。

## 二十一、答案提示显示 slug 的 bug 修复（2026-06-14）

### 21.1 现象

练习/考试答题错误后，反馈提示显示：

> 正确答案是：gui-zhi-jia-houpo-xingzi-tang

而不是方剂的显示名称「桂枝加厚朴杏子汤」。

### 21.2 根因

`1→0`（症状→方名）和 `2→0`（药物组合→方名）题型的 `q.correct` 存储的是卡片 ID（slug），用于判定对错。但 `showExamFeedback` 直接把 `q.correct` 显示给用户，导致出现 `gui-zhi-jia-houpo-xingzi-tang` 这类机器标识。

其他题型：

- `0→1` 的 `correct` 是症状文本字符串
- `0→2` / `0→contra` 是数组
- `0→usage` 是煎服法文本

这些题型本来就没问题。

### 21.3 修复

新增 `formatCorrectAnswer(q)` 辅助函数：

```js
function formatCorrectAnswer(q) {
  if (q.type === '1→0' || q.type === '2→0') {
    return slugToName(q.correct);
  }
  return Array.isArray(q.correct) ? q.correct.join('、') : q.correct;
}
```

并在 `showExamFeedback` 的「未作答」和「回答错误」分支中统一使用它。同时把「回答正确」提示也扩展为对 `1→0` 和 `2→0` 都显示方名。

### 21.4 验证

- 直接调用 `formatCorrectAnswer({type:'1→0', correct:'gui-zhi-jia-houpo-xingzi-tang'})` 返回方名。
- 打开页面进入练习模式，选择错误选项后，反馈提示显示为「桂枝加厚朴杏子汤」。

### 21.5 备份

- `C:\Users\Chen\Desktop\经方学习系统（旧版）\app\archive\index-before-correct-answer-bug.html`

### 21.6 经验

- **显示给用户的必须是「人话」，不能直接把内部 ID 抛出来。**
- 同一字段在不同题型下可能是 ID、数组或文本，显示前要做类型分支。

### 25. 经方剂量换算标准体系建立（SH-20260619-013）

**变更内容**：

**关键决策**：
- **四档标准数值**：
  - 教材：1两=3g（李时珍《本草纲目》：「古之一两，今之一钱」）

  - 原方：1两=15g（仝小林简化版，柯雪帆15.625g/两的临床取整）

- **药物密度**：半夏130g/升（柯雪帆实测）、粳米180g/升（文献均值）、杏仁70g/升（实测均值）等

**技术实现**：
- `convertDosage` 函数从支持6种单位扩展到14种（两/钱/斤/分/两半/升/合/合半/枚/个/铢/复合铢/茎/尺/如鸡子大）

### 27. SP 批量生成：子 Agent 文件保存不可靠（SH-20260618-032 ~ SH-20260619-011）

**现象**：
Batch 4-9 共 35 例 SP 病例，多次出现子 Agent 声称已保存 JSON 到根目录，但主 Agent `ls` 验证时文件不存在的情况。

**根因分析**：
- 子 Agent 的 Python `open(filename, 'w')` 写入时，工作目录上下文可能因环境解析问题写入其他位置（如 Python 临时目录或子 Agent 私有目录）
- 子 Agent 可能在输出中声称已保存，但写入操作实际失败（如磁盘空间不足、权限问题）
- 子 Agent 会话结束后，其工作目录可能被清理，导致文件丢失

**修复方案**：
- 主 Agent 在子 Agent 返回后，**立即用 `ls` 或 `Read` 验证文件存在**
- 如果不存在，主 Agent 直接用 `Write` 或 Python 脚本重新写入（主 Agent 的 Write 工具直接写入当前工作目录，路径确定性更高）
- 临时文件保存后立即用 `json.load()` 验证 JSON 合法性，然后再合并到 `sp_cases.json`

**教训**：
- 子 Agent 的文件写入不可信，必须通过主 Agent 二次验证
- 重要文件（如 SP 病例 JSON）应优先使用主 Agent 的 `Write` 工具直接写入，而非依赖子 Agent 的 `open()`
- 子 Agent 适合生成内容（文本/JSON 字符串），主 Agent 负责持久化到磁盘

### 28. Windows 终端编码与中文验证的死循环（SH-20260618-032 ~ SH-20260619-012）

**现象**：
`governance.py check-sp` 输出中文症状名在 PowerShell 中显示为乱码（如 `ȶ` 代替 `发热恶寒`），无法直接阅读缺失症状列表。连续 9 个批次都受此困扰。

**根因分析**：
- PowerShell 默认使用 GBK 代码页（936），而 Python 输出 UTF-8 字符串时无法正确解码
- 使用 `py -c "print(...)` 回显中文，终端显示为乱码或问号，无法判断内容
- 一度误以为是数据本身损坏（JSON 编码错误），浪费大量时间排查

**修复方案**：
- 所有中文验证结果写入临时文件（`temp_missing.txt`），然后用 `Read` 工具读取
- 症状索引的 `json.dump` 必须使用 `ensure_ascii=False`，否则写入文件后也是 Unicode 转义序列
- 不再依赖任何 Shell 回显判断中文内容，包括 `echo`、`cat`、`python -c print`

**教训**：
- Windows PowerShell 处理中文 = 永远以文件内容为准，终端回显不可信
- 验证类工具（governance.py）应增加 `--output-file` 参数，默认输出到文件而非 stdout
- 在 Windows 上处理 JSON 中的中文键名时，读写必须用 `encoding='utf-8'` + `ensure_ascii=False`

### 29. 症状索引自动分类的边界误差（SH-20260618-026 ~ SH-20260619-012）

**现象**：
Batch 3-9 共补充 247 个症状（385 - 138），其中 143 个用自动规则分类。部分症状归类不够精确：
- "既往感冒史" → 自动分到「旧病/诱因」，实际应为「头身」（感冒属于外感表证）
- "无胸胁苦满" → 自动分到「胸腹/腹胀」，实际应为「排除项」
- "自我处理无效" → 自动分到「旧病/诱因」，实际应为「行为描述」

**根因分析**：
- 自动分类基于关键词匹配（如含「旧」「既往」→ 旧病/诱因），没有医学语义理解
- 否定词（"无"、"不"）和复合词（"自我处理"）无法被简单规则正确分类
- 症状索引的分类主要用于生成器的 `symptom_pool` 组织，不影响病例生成逻辑

**修复方案**：
- 核心症状（如 "大烦渴不解"、"身大热"、"呕不止"）已手动补充精确表达和正确分类
- 边缘症状（如 "既往感冒史"、"自我处理无效"）保持自动分类，后续在 symptom index v2 中统一人工校对
- 新增自动分类规则时，优先保证大类正确（寒热/汗出/二便/饮食/头身/胸腹），子类可容忍误差

**教训**：
- 自动分类规则适合快速填充，不适合精确分类；v1.0 → v2.0 的升级必须人工校对
- 症状索引的 "expressions" 字段即使写 "（患者表达待补充）" 也不影响生成器功能，因为生成器主要用 `symptom_pool` 和 `clue_map`
- 但前端展示时如果调用 symptom_expression_index 显示口语表达，这些占位符会暴露质量缺陷

### 30. 难度 3 病例的「主诉模糊化」设计不足（SH-20260619-004 ~ 011）

**现象**：
Batch 9 的 8 个难度 3 病例，部分主诉（如 sp-037 麻黄汤）的 `revealed_symptoms` 仍然包含 4-5 个关键症状，与难度 1 版本（sp-005 麻黄汤）的差异仅在于字数少，而非信息隐藏。

- 难度 1 的 revealed_symptoms 有 5-6 个，难度 3 也有 3-4 个，差距不够显著
- 理想情况下，难度 3 主诉的 revealed_symptoms 应只保留 1-2 个非关键症状（如 "不舒服"、"有点累"），关键症状（如 "无汗"、"喘"）必须靠医生追问（inquiry L1）才给出

**修复方案**：
- 在 SP 生成器的 v0.2 版本中，增加 `difficulty → 主诉症状数` 映射：
  - diff1：revealed_symptoms = 5-7（核心症状全部暴露）
  - diff2：revealed_symptoms = 3-4（部分核心症状暴露）
  - diff3：revealed_symptoms = 1-2（只暴露非关键症状，关键症状需追问）

  - silent-elderly-male：回答极简，只给 1 个症状，其他需反复追问

- 难度不应该是「字数多少」或「噪声多少」，而应该是「关键信息获取的难易程度」
