## 一、之前的工作方式 vs. 今天的工作方式

| 维度 | 之前（单线模式） | 今天（多 Agent 并行模式） |
|------|----------------|------------------------|
| **角色分工** | AI 执行者，用户等待结果 | 用户是架构师/协调者，AI 提供分析框架和提示词 |
| **问题处理** | 直觉式，遇到 bug 逐个修复 | 控制论系统分析，先定位回路断裂点 |
| **执行方式** | 串行：做 A → 等反馈 → 做 B | 并行：A/C/D 同时启动，结果汇总后启动 B |
| **验证机制** | 单点验证：我做，你验 | 交叉验证：多 Agent 独立报告，架构师交叉比对 |
| **错误定位** | 试错式：改一下，看看对不对 | 假设式：先假设根因，设计验证实验，再确认 |
| **效率** | 低（等待时间长） | 高（多线并行，用户主导协调） |
| **用户参与度** | 被动（看结果） | 主动（分发任务、收集结果、做决策） |

## 二、控制论分解方法（核心方法论）

### 2.1 问题识别：开环 vs. 闭环

把系统看作**控制回路**：

```
[输入] → [控制器] → [执行器] → [被控对象] → [输出] → [反馈] → [输入]
```

**故障分析**：
- 如果输入有了，输出没有 → 检查回路中哪个环节断裂
- 今天 V9 卡片点击问题：`setPage('learn')` 是输入，但 `viewLearn` 没显示 → 检查 `_listeners` 为空 → 根因：`subscribe` 未注册

### 2.2 模块分解：独立性原则

把系统分解为**独立控制回路**（R1, R2, R3...），每个回路：
- 有独立的输入/输出
- 与其他回路**无直接依赖**（只共享状态）
- 可以分配给不同 Agent 并行处理

**判断独立性的标准**：
- 修改的是不同文件 → 可并行
- 修改同一文件但不同函数 → 可并行（但需注意合并）
- 修改同一文件的同一函数 → 串行

### 2.3 假设-验证-修正

| 步骤 | 操作 | 示例 |
|------|------|------|
| 假设 | 提出根因假设（按概率排序） | "subscribe 被导入但从未调用" |
| 验证 | 设计实验验证假设 | 添加调试日志，检查 `_listeners.size` |
| 修正 | 确认假设后修复 | 在 `init()` 中注册 `subscribe` |
| 备选 | 假设错误时下一步 | 检查模块是否重复加载 |

## 三、多 Agent 并行规范

### 3.1 对话命名规范

| 类型 | 命名格式 | 示例 |
|------|---------|------|
| 主控对话 | `项目名-角色-任务` | `经方V9-架构师-交互界面还原` |
| 子 Agent 对话 | `项目名-模块名-动作` | `V9-学习页交互还原` |
| 备用对话 | `项目名-模块名-补充` | `V9-剂量换算还原` |

### 3.2 提示词模板（5 要素）

每个子 Agent 的提示词必须包含：

1. **任务目标**：一句话说清楚做什么
2. **已知信息**：文件路径、已知状态、已知问题
3. **具体执行步骤**：1. 2. 3. 4. 按顺序列出
4. **安全约束**：备份命令、文件锁、不修改的范围
5. **返回格式**：5 个标准部分（已完成清单、已知问题、修改文件、测试结果、假设错误时下一步）

### 3.3 安全规则（铁律）

| 规则 | 说明 |
|------|------|
| **修改前必备份** | `node -e "fs.copyFileSync('src', 'archive/src')"` |
| **单文件责任制** | 每个 Agent 只修改一个主要文件 |
| **不删除只注释** | 保留原始代码，用 `// DEBUG:` 或 `// [V8 REF]` 标记 |
| **返回必含 5 部分** | 已完成 / 问题 / 文件 / 测试 / 备选方案 |
| **Git 分支** | 建议每个 Agent 一个分支，完成后合并 |

### 3.4 并行执行顺序

```
[分析阶段] 架构师分析 → 分解为独立回路 → 判断依赖关系
       ↓
[启动阶段] 无依赖的 Agent 并行启动（A + C + D）
       ↓
[收集阶段] 收集各 Agent 报告 → 交叉验证 → 确认无冲突
       ↓
[串行阶段] 依赖 Agent 启动（B 依赖 A）
       ↓
[汇总阶段] 最后启动样式/汇总 Agent（E）
       ↓
[集成阶段] 架构师做集成测试 → 冒烟测试 → 验收
```

## 四、交叉验证机制

### 4.1 多源比对

当多个 Agent 报告同一系统的不同部分时：
- 如果 Agent 2 说"状态管理正常"，Agent 3 说"DOM 正常"，但 Agent 4 说"链路断裂" → 根因在中间环节
- 如果两个 Agent 的修改可能冲突 → 架构师做合并决策

### 4.2 已知问题清单整合

每个 Agent 返回的"已知问题"要汇总到主控对话：
- 标记优先级（P0/P1/P2）
- 分配修复责任人（哪个 Agent 修复）
- 决定哪些留到后续迭代

## 七、经验教训

### 7.1 做得好的地方

1. **控制论分析精准**：先定位 `_listeners` 为空，再追溯到 `subscribe` 未注册，避免了在无关代码上浪费时间
2. **并行策略正确**：A/C/D 三个 Agent 同时启动，互不冲突
3. **提示词规范**：每个 Agent 返回格式一致，便于汇总
4. **备份意识**：每个 Agent 都执行了备份

### 7.2 可以改进的地方

1. **Vite 服务器稳定性**：需要确保后台任务持续运行，避免反复重新连接
2. **CSS 样式滞后**：功能 Agent 完成后，样式 Agent 才开始，可能导致功能可用但视觉效果不一致
3. **Agent B 被覆盖**：剂量换算被 Agent A 顺便做了，说明分解粒度可以更细（或提前确认功能边界）
4. **集成测试时机**：应该在每个 Agent 完成后就做局部验证，而不是等全部完成

### 7.3 下一步建议

1. **建立 Agent 执行手册**：把本次的提示词模板、命名规范、安全规则写成 Skill
2. **自动化测试脚本**：为每个 Agent 创建独立的测试脚本，验证其修改是否生效
3. **样式先行**：下次功能迁移前，先让样式 Agent 提取 V8 的全部 CSS，作为功能 Agent 的参考
4. **Git 工作流**：每个 Agent 一个分支，用 PR 合并，方便回滚
