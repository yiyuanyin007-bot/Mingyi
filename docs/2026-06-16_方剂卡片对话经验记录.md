## 一、核心经验（按优先级排序）

### 1.1 处方解析：从"位置正则"到"已知药名精确匹配"

**问题**：早期用正则 `([^，。、\s]{1,6}[\d]+[克g])` 按"位置"匹配药名+剂量，导致：
- "师处方：柴胡10克，黄芩10克，半夏10克" → 解析出 "夏10克"（截断）
- "柴胡10克，黄芩10克，10克" → 解析出 "10克"（无药名）

**解决**：
1. 建立 291 个已知药名库（从 35 张卡片 herbs + 常见别名）
2. 按药名精确匹配：搜索每个已知药名，再找后面的数字+单位
3. 按长度降序匹配：先匹配"炙甘草"再匹配"甘草"，防止截断
4. 边界检查：药名前后不能是中文汉字（避免匹配到别的词内部）

**结果**：34 个医案全部解析成功，每案 10-17 味药。

**经验**：任何从非结构化文本提取结构化数据，"已知实体匹配"比"位置正则"可靠得多。

### 1.2 file:// 协议下 fetch JSON 会失败

**问题**：用户双击 `index.html` 打开（file:// 协议），`fetch('../data/xxx.json')` 报跨域错误。导致：
- `herb_alias_map.json` 加载失败 → 药名别名映射不生效
- 点击"赤芍"找不到"芍药" → 弹窗显示空
- 点击"去学习"基于空数据生成 → 无反应

**尝试过的方案**：
- A. 硬编码 150 个药名在 `index.html` JS 里 → 能用，但维护困难，mobile.html 无法共享
- B. 检测 file:// vs http://，双路径加载 → 代码复杂度增加
- C. `<script src="herb-aliases.js">` 加载独立 JS → 需要脚本从 JSON 自动生成，但 file:// 可用，index.html + mobile.html 共享

**最终建议**：方案 C（尚未实施）。`data/herb_alias_map.json` 保持唯一真相源，脚本自动生成 `app/herb-aliases.js`，HTML 通过 `<script src>` 加载。

**经验**：在决定加载策略前，先确认用户的使用方式（双击打开 vs 服务器访问）。

---

### 1.3 用户不会开控制台

**问题**：反复建议"打开控制台输入 `generateDailyReport()`"，用户明确说"我不懂用控制台，不懂在哪里"。

**解决**：
- 顶部栏新增 **📊 今日学习** 按钮，点击直接弹出学习报告
- 弹窗内显示"已查看 N 次"，无需手动查询
- 弹窗内加 **导出学习数据** 按钮，一键下载 JSON

**经验**：所有交互痕迹必须用户可见。后台记录不等于交互，只有用户能感知到的才叫交互。

---

### 1.4 弹窗内跳转需要 `setTimeout`

**问题**：`onclick="goToLearn('id');closeModal()"` 两个函数冲突，点击后弹窗关闭但页面不跳转。

**解决**：统一用 `handleModalGoToLearn(id)` → 先 `closeModal()`，50ms 后 `goToLearn(id)`，避免 DOM 冲突。

**经验**：弹窗内的事件处理需要独立的"关闭→跳转"封装函数，不要直接串两个操作。

---

### 1.5 视觉规范必须统一 CSS 变量

**问题**：版本 B 预览版用自定义渐变、紫/橙/绿主题色，与主页风格不一致。

**解决**：所有新样式必须使用主页已有的 CSS 变量（`--bg-panel`, `--border`, `--accent`, `--text-primary` 等），确保 dark/light 主题自动切换。

**输出**：`docs/视觉设计规范-V1.md` — 药名、剂量、合方标签、分隔符、信息层级的统一标准。

**经验**：新增样式前先读取现有 CSS 变量体系，不要写死颜色。圆角统一 10px，字体统一 13px/14px。

---

### 1.6 内容呈现：从"大段文字"到"结构化卡片"

**问题**：用户反馈"一大段字看着不舒服，太琐碎"。

**解决**：
- 言论（teacher_notes）→ 拆分为 bullet points（经验要点）
- 医案（clinical_cases）→ 拆分为"患者画像标签 + 症状描述 + 处方框 + 疗效框"
- 处方 → 药名加粗可点击 + 剂量小字灰色 + "、"分隔
- 合方 → 标签样式（灰底彩字，悬停反色）

**经验**：临床内容必须用"扫描式"结构，不是"阅读式"排版。用户要的是"这个患者什么情况→用了什么方子→结果如何"，不是一篇叙事文。

---

### 1.7 类方学习：按 lineage 分组，不是简单列表

**问题**：点击药名显示"出现在以下方剂中"的简单列表，用户无法看出"这是柴胡剂系列"还是"桂枝剂系列"。

**解决**：按 `lineage.base_formula` 分组，如：
- 柴胡剂系列（3方）：大柴胡汤、小柴胡汤、柴胡加龙骨牡蛎汤
- 桂枝剂系列（2方）：桂枝汤、柴胡桂枝汤

**经验**：类方学习的核心不是"哪些方含这个药"，而是"这个药在不同类方中的作用差异"。分组是认知脚手架。

---

### 1.8 别名映射必须前端可用

**问题**："赤芍、白芍都属于芍药"，但前端没有映射表 → 点击赤芍找不到芍药相关方。

**解决**：建立 `alias_to_standard` 映射（赤芍→芍药、生甘草→甘草、红枣→大枣），加载到前端 `window.HERB_ALIAS_MAP`。

**经验**：别名映射是数据设计（方剂卡片对话），但加载策略是前端实现（操作系统对话）。两方需要对齐"映射表存在哪里、以什么格式暴露"。

## 二、跨对话框协作经验

### 2.1 数据格式先对齐，前端再渲染

**事件**：ROUND 1 中前端写了 `renderReferences()` 基于假设的数据结构，但批量注入时实际字段名/类型不一致 → 前端渲染失败。

**教训**：
1. 方剂卡片对话先定义并输出 JSON Schema（如 `prescription_structured: [{name, dose}, ...]`）
2. 操作系统对话确认理解 Schema 后再写渲染代码
3. 双方用同一份 "sample data"（如大柴胡汤的 references）做冒烟测试

### 2.2 加载策略是灰色地带，需要显式决策

**事件**：file:// 下 fetch JSON 失败，两方在"硬编码 vs 外部文件"上反复拉锯。

**教训**：
- 数据内容（哪些别名、哪些类方）→ 方剂卡片对话负责
- 加载方式（硬编码/JS 文件/构建工具）→ 操作系统对话负责
- 但两方必须在"映射表以什么格式暴露给前端"上达成一致

**建议红线**：
- 方剂卡片对话输出：`data/herb_alias_map.json`（唯一真相源）
- 操作系统对话决定：通过 `<script src>` 加载 JS 文件，或通过构建工具注入
- 两方确认：`window.HERB_ALIAS_MAP` 对象在页面加载后必须可用

### 2.3 验证分工：数据层 vs 交互层

| 验证项 | 方剂卡片对话 | 操作系统对话 |
|--------|------------|------------|
| JSON 合法性 | ✅ `json.load()` | 不直接验证 |
| 字段完整性 | ✅ schema check | 依赖数据层 |
| 括号/语法平衡 | 不直接验证 | ✅ JS 代码扫描 |
| 点击有响应 | 不直接验证 | ✅ 浏览器测试 |
| 弹窗显示内容 | 确认数据正确 | ✅ 渲染正确 |
| 跳转/加载 | 不直接验证 | ✅ 端到端测试 |

**教训**：不能一方做完全部验证。数据层验证通过后，交互层仍需独立验证。

## 三、已踩的坑（不再重复）

| 坑 | 根因 | 解决 | 预防 |
|---|------|------|------|
| 处方解析出"夏10克" | 正则按位置匹配，不识别药名边界 | 已知药名精确匹配 + 长度降序 | 所有文本提取先用实体库匹配 |
| file:// 下 fetch 失败 | 没确认用户打开方式 | 硬编码 fallback + 后续改 JS 文件加载 | 任何加载策略先问"用户怎么打开" |
| 弹窗内跳转无反应 | `goToLearn();closeModal()` 冲突 | `handleModalGoToLearn()` 封装 | 弹窗内所有跳转/关闭用独立函数 |
| 控制台建议用户不会 | 假设用户是开发者 | 顶部栏加按钮，弹窗内显示 | 所有交互必须零门槛 |
| 视觉风格不一致 | 新样式用自定义颜色 | 全部用 CSS 变量 `--var` | 新增样式前先读现有 CSS 变量 |
| 别名映射不生效 | 外部 JSON 加载失败 | 硬编码 150 个别名 fallback | 关键数据必须有 fallback 机制 |
| 大段文字难读 | 没做内容结构化 | 拆分为 bullet points + 卡片 | 临床内容必须扫描式结构 |
