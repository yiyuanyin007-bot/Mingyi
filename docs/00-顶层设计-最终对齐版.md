## 一、项目定位与设计原则

### 1.1 项目定位

**项目名称**：《伤寒论》《金匮要略》方剂思维训练系统

**核心目标**：以倪海厦注解的《伤寒论》《金匮要略》为知识底座，构建方剂思维训练系统，提升中药开方思路。

**系统定位**：

| 组件 | 定位 | 说明 |
|------|------|------|
| 卡片体系 | 进度管理工具 | 筛选今天学什么、追踪掌握度、安排艾宾浩斯复习 |
| 真正学习 | 读原文 + AI导师对话 | 发生在卡片体系之外/之后，是学习的核心环节 |
| 前端程序 | 可视化呈现 | 用户自己写，读取JSON文件，调用AI导师API |
| WorkBuddy（佐助） | 后台支持 | 卡片提炼、设计文档、后台任务，不参与实时对话 |

### 1.2 设计原则（必须对齐）

1. **学习是为了临床，临床是为了把事情做好** —— 北极星原则，所有设计决策以此为准。
2. **临床疗效 > 学派立场** —— 倪海厦的扶阳派视角是输入来源，但不是判断标准。标准是：这个方在你的病人身上是否有效。
3. **阶段划分明确**：
   - 阶段一（现在）= 条文 → 卡片 → 训练
   - 阶段二（有临床数据后）= 自己的医案/录音 → 反哺卡片
4. **JSON > MD** —— JSON是真相源，MD是从JSON导出的只读视图。程序只读JSON。
5. **根目录简洁** —— 只保留文件夹、说明文件、常用JSON。其他内容按分类原则组织，分类依据写清楚。
6. **学习 = 把不能做的变成能做** —— 学习是产出过程，不是记忆过程。系统要让用户看到自己的进步可视化。

### 1.3 教学系统设计原则

（借鉴Matt Pocock的teach技能设计理念）

#### 1.3.1 教学三角模型

深度学习需要三样东西：
- **知识（Knowledge）**：来自高质量、高可信度的资源
- **技能（Skills）**：通过交互式课程获得的动手能力
- **智慧（Wisdom）**：来自与其他学习者和从业者的真实互动

在RESOURCES.md充实之前，重点应该是寻找高质量资源。永远不要信任参数化知识（模型记忆）。

#### 1.3.2 MISSION.md - 学习动机文档

**定位**：所有教学决策都应追溯到此文档。用户的"为什么学"比"学什么"更重要。

**位置**：`03-工作项目/伤寒论金匮要略训练系统/MISSION.md`

**内容结构**：
- 我是谁（身份、背景、临床阶段）
- 为什么学《伤寒论》（临床痛点、具体场景）
- 成功标准（3个月后能做什么）
- 学习方式偏好（视觉/听觉/动手）

#### 1.3.3 学习记录（Learning Records）

**定位**：记录非显而易见的教训和关键洞察，用于计算最近发展区（ZPD）。

**位置**：`03-工作项目/伤寒论金匮要略训练系统/learning-records/*.md`

**格式**（类似软件ADR）：
- 状态（已确认/待验证/已推翻）
- 背景（遇到了什么问题）
- 决策（学到了什么关键洞察）
- 后果（下次遇到类似情况怎么做）
- 关联卡片（相关的方剂卡片ID）

#### 1.3.4 ZPD驱动训练（最近发展区）

**定义**：ZPD（Zone of Proximal Development）= 用户"已经会"和"还不会"之间的区域。训练应该始终在ZPD内进行。

**计算方法**：
- 输入：用户所有卡片的8个向量掌握度状态
- 输出：今日应该训练的向量列表（按优先级排序）

**优先级规则**：
- `status="正在学习"` 且 `streak_right < 3` → 高优先级（在ZPD内，需要巩固）
- `status="已遗忘"` → 高优先级（需要重新学习）
- `status="未知"` → 中优先级（可以开始学）
- `status="已掌握"` 且 `level=5` → 低优先级（只需抽检）

**实现**：WorkBuddy每日凌晨任务生成时，基于ZPD计算今日学习任务。

#### 1.3.5 参考文档与课程概念

**参考文档（reference/*.html）**：
- 定位：课程的压缩精华，适合快速查阅
- 格式：HTML（可交互、可打印、可分享）

**课程（lessons/*.html）**：
- 定位：每节课教授一件紧密限定的事
- 格式：自包含HTML，短小、可快速完成、给用户胜利感
- 触发：当用户 `status="未知"` 时，系统生成/推荐一节课

## 二、知识卡片体系

### 2.1 颗粒度

- **一张卡片 = 一个方剂**
- 基础方与加减变体各为独立卡片
- 变体卡片通过 `parent_formula_id` 字段指向基础方卡片（单向，只挂一个方剂）
- 基础方卡片通过 `variants` 字段列出所有变体卡片 ID

**举例**：
- `gui-zhi-tang.json` → 桂枝汤（主方）
- `gui-zhi-jia-ge-gen-tang.json` → 桂枝加葛根汤（变体，parent=`gui-zhi-tang`）

**跨方剂鉴别内容处理**：跨方剂的鉴别讨论不作为经验卡片存储，在AI导师对话中讨论即可，三级笔记存在 `ai_tutor/notes/` 目录里。

### 2.2 标签体系

每张卡片包含以下标签维度，支持灵活查询：

| 标签类型 | 字段名 | 说明 | 示例 |
|---------|--------|------|------|
| 方名 | `formula` | 方剂名称（处方名称标签） | `桂枝汤` |
| 角色 | `role` | 主方 / 加减变体 | `主方` / `加减变体` |
| 类型 | `type` | 加减变体 / 合方 / 主方 | `加减变体` / `合方` / `主方` |
| 来源 | `source` | 条文 / 医案 / 两者皆有 | `条文` / `医案` / `条文+医案` |
| 篇目 | `chapter` | 所属篇目 | `太阳病篇` / `痉湿暍篇` |

**查询场景**：
- 随机学习：任意拉取单张卡片
- 体系学习：按 `formula: 桂枝汤` 拉取（主方 + 所有加减变体）
- 按篇目学习：按 `chapter: 太阳病篇` 拉取（该篇所有方剂）
- 按症状学习：过滤 `symptoms` 数组字段

### 2.3 训练向量（原"五个训练维度"）

每张卡片支撑以下**8个训练向量**。注意：不是"维度"，是**向量**——因为"从方名到症状"和"从症状到方名"是两个独立方向，训练题型不同。

**5个认知点（维度）**：

| # | 维度名 | 说明 |
|---|--------|------|
| 0 | **方名** | 这个方叫什么名字（标识符，不作为掌握度追踪单元） |
| 1 | **使用场景** | 什么症状/证候下使用 |
| 2 | **药物组成** | 方中有哪些药 |
| 3 | **方剂用法** | 怎么煎、怎么服、禁忌 |
| 4 | **辨证机理** | 为什么这个方治这个证（病机） |

**8个训练向量**（由维度两两组合，方向不同即不同向量）：

| 向量 | 方向 | 训练题型举例 |
|------|------|---------|
| 0→1 | 方名 → 症状 | "桂枝汤的使用场景是？" |
| 1→0 | 症状 → 方名 | "头痛发热汗出恶风，选方？" |
| 0→2 | 方名 → 药物 | "桂枝汤的药物组成是？" |
| 2→0 | 药物 → 方名 | "桂枝、芍药、甘草、生姜、大枣，是哪首方？" |
| 0→3 | 方名 → 用法 | "桂枝汤怎么煎服？" |
| 3→0 | 用法 → 方名 | "以水七升微火煮取三升，是哪首方？" |
| 0→4 | 方名 → 病机 | "桂枝汤的辨证机理是？" |
| 4→0 | 病机 → 方名 | "风邪袭表营卫不和，选方？" |

**映射唯一性原则**：同一向量方向下，题干→答案的映射必须唯一。如果相同题干对应不同答案（如"头痛发热"同时对应桂枝汤和麻黄汤），说明映射不唯一，需通过制卡迭代流程解决（见2.6节）。映射不唯一时，制卡需备注`allow_multiple: true`（见2.4节）。

**掌握度追踪单位**：按**向量**追踪（8个向量各有独立掌握度状态），不按维度。详见第四章。

**掌握度字段说明**（`mastery.向量ID` 对象）：
- `label`：向量语义标签（用于前端展示）
- `level`：艾宾浩斯等级（0-5，见第四章）
- `status`：掌握状态（`未知`/`从未掌握`/`正在学习`/`已掌握`/`已遗忘`）
- `last_result`：上次答题结果（`right`/`wrong`/`null`）
- `last_review`：上次复习日期（ISO日期/`null`）
- `streak_right`：当前等级下连续答对次数
- `streak_wrong`：当前等级下连续答错次数
- `total_rights`：累计答对次数（历史累计，不随等级重置）
- `total_wrongs`：累计答错次数（历史累计，不随等级重置）
- `history`：最近10次答题记录（格式：`[{"date":"2026-06-11","result":"right"}]`）

**data新增字段**：
- `allow_multiple`：布尔值，标记该卡片在出题时是否应出多选题（当映射不唯一时）
- `mapping_note`：文字备注，说明映射不唯一的详细情况

### 2.5 经验卡片 JSON 结构

经验卡片是独立文件，记录真实临床经验（倪海厦医案、他人经验、用户自己的临床心得）。AI导师讨论产生的三级笔记独立存储在 `ai_tutor/notes/` 目录，不存入经验卡片。

```json
{
  "id": "gui-zhi-tang_exp-001",
  "type": "experience_card",
  "parent_formula_id": "gui-zhi-tang",
  "title": "倪师：桂枝汤为风伤卫之主方",
  "source": "倪海厦",
  "source_type": "条文注解",
  "content": "（临床经验描述，如倪师原话、医案记录、个人心得等）",
  "content_history": [
    {"version": "v1", "date": "2026-06-11", "backup_file": "archive/gui-zhi-tang_exp-001_v1.md"}
  ],
  "tags": ["桂枝汤", "倪海厦", "条文注解", "太阳病篇"],
  "created_at": "2026-06-11T00:00:00",
  "updated_at": "2026-06-11T00:00:00"
}
```

**字段说明**：
- `parent_formula_id`：只挂一个方剂（单向关联）
- `source_type` 枚举：`倪海厦`/`其他典籍`/`个人医案`/`他人经验`
- `content`：临床经验描述（倪师原话、医案记录、个人心得等）
- `content_history`：版本历史，每次覆盖写入前先备份临床经验内容

### 2.6 制卡迭代流程规范

**核心原则**：映射必须一一对应。如果相同症状组合对应不同方剂，说明卡片设计有问题，需通过迭代流程解决。

**流程**：

```
第1步：收集原始材料
  - 大规模搜集阶段，找出大量相关原始材料
  - 材料可能是标注、页码标注、需要背诵的内容
  - 存入 `02-读书笔记/理论/raw_materials/` 目录

第2步：制作删减版（Alpha版）
  - 从原始材料中提取核心信息，制作Alpha版卡片
  - Alpha版可以较繁复，保留细节

第3步：横向对比
  - 完成Alpha版后，将所有Alpha版卡片进行横向对比
  - 发现"症状相同但方剂不同"的矛盾点

第4步：回溯与迭代
  - 发现矛盾后，回到原始材料库，寻找被删掉的细节
  - 将这些细节重新添加进去，修正映射关系
  - 版本演进：B测 → C测 → 1.1 → 1.2 → 1.3

第5步：留存记录
  - 所有迭代版本全部留存记录
  - 存于 `02-读书笔记/理论/card_versions/` 目录
```

## 三、学习流程

### 3.1 卡片堆状态机

**核心概念**：卡片在任意时刻处于以下状态之一：

```
┌─────────────┐
│   卡池       │ ← 未进入复习流程（新卡片）
└──────┬──────┘
       │ 学习完成，连续对3次
       ▼
┌─────────────┐
│  等待区      │ ← 未到艾宾浩斯时间，不出现
└──────┬──────┘
       │ 到达艾宾浩斯时间点
       ▼
┌─────────────┐
│ 待复习堆     │ ← 已弹出，等待用户复习（滞留逻辑：不复习就一直留在这）
└──────┬──────┘
       │ 用户完成复习（连续对3次）
       ▼
┌─────────────┐
│  等待区      │ ← 回到等待区，进入下一艾宾浩斯窗口
│ (下一窗口)   │
└──────┬──────┘
       │ 所有艾宾浩斯周期完成
       ▼
┌─────────────┐
│ 待随时抽检堆  │ ← 可被随机抽取测试（30天周期完成后启动）
└─────────────┘
```

**状态转移规则**：

| 当前状态 | 触发事件 | 下一状态 |
|---------|---------|---------|
| 卡池 | 学习完成，连续对3次 | 等待区 |
| 等待区 | 到达艾宾浩斯时间点 | 待复习堆 |
| 待复习堆 | 用户当天未复习 | 仍待复习堆（滞留） |
| 待复习堆 | 用户复习，连续对3次 | 等待区（下一窗口）或待随时抽检堆（所有窗口完成） |
| 待随时抽检堆 | 随机抽取，测试 | 待复习堆（如果答错）或仍待随时抽检堆（如果答对） |

### 3.2 完整学习循环

```
【每天开始】
  │
  ├─ 选项A：快速筛选测试（3-5题）
  │    - 用户选症状/方剂，或系统按艾宾浩斯自动出题
  │    - 目的：找出"不会的" = 今日学习目标
  │    - 答错的卡片维度 → 进入今日学习列表
  │    - 答对的卡片维度 → 如果连续在快速筛选中对≥2次，暂时移出今日学习列表（但仍在正常复习队列）
  │
  ├─ 选项B：跳过快速筛选
  │    - 系统按艾宾浩斯窗口自动生成今日复习列表
  │    - 取所有 `next_review` ≤ 今天的维度
  │
  ├─ 第二步：原文学习 + AI导师对话（核心学习环节）
  │    - 系统展示该卡片的原文（source_text）
  │    - 用户在前端程序里跟AI导师对话
  │    - 用户语音→转文字，输入理解/疑惑/辩论
  │    - AI导师根据原文+用户输入回应
  │    - 对话持续，直到用户说"确认结束"
  │    - AI生成"三级笔记" → 存入 `ai_tutor/notes/` 目录（独立文件，不存入经验卡片）
  │    - 原始对话记录存入 `session_logs/`
  │
  ├─ 第三步：回归正常复习流
  │    - 该卡片维度回到正常复习队列
  │    - 在后续正常复习中，如果用户连续选对3次 → 升级
  │    - 如果答错 → 不升级，留在当前等级
  │
【一天结束】
  ├─ 生成今日学习总结（学了哪些卡片、哪些维度、问答记录摘要）
  ├─ 更新掌握度状态
  └─ 安排明天需要复习的内容
```

### 3.3 AI导师系统 — 详细工作流程

**AI导师 ≠ WorkBuddy（佐助）**。AI导师是用户前端程序里集成的独立AI接口，用户接自己的API（目前用Kimi）。

#### 第一次请求

```
前端程序 调用 LLM API：
  system_prompt = prompt.md 的内容
  messages = [
    {role:"system", content: prompt.md},
    {role:"user", content: "【当前学习内容】\n{卡片source_text}\n\n【历史笔记】\n{已有三级笔记(如有)}"}
  ]
```
LLM返回第一句引导语 → 前端展示 → **对话开始**

#### 后续对话（第2次及以后请求）

```
前端程序 调用 LLM API：
  messages = [
    {role:"system", content: prompt.md},   ← 始终带着
    {role:"assistant", content: "第一句引导语..."},
    {role:"user", content: "我的回复1..."},
    {role:"assistant", content: "LLM回复1..."},
    ...（完整对话历史）
    {role:"user", content: "我的最新回复"}
  ]
```
**不用每次都重新发原文** —— 对话历史里已经有了。

#### 结束标志

用户说"确认结束"（或prompt里定义的其他结束词）→ 前端在最后一次请求里加一句：
```
"用户已确认结束。请根据以上对话，生成三级笔记。"
```
LLM返回三级笔记内容 → 前端接收 → **写入 `ai_tutor/notes/` 目录**

#### 写入机制

```
1. 在 `ai_tutor/notes/` 目录创建/更新三级笔记文件（如 `trace_20260611_gui-zhi-tang.json`）
2. 把三级笔记内容写入该文件（如已存在，先备份旧版到 `ai_tutor/notes/archive/`）
3. 把原始对话写入 `session_logs/2026-06-11_xxx.jsonl
```

#### prompt.md 文件位置

```
03-工作项目/伤寒论金匮要略训练系统/ai_tutor/prompt.md
```

用户可在前端直接修改 prompt.md，不需要改代码。

## 四、掌握度追踪（v3.0）

### 4.1 基本单位

**卡片ID × 向量** —— 8个向量（`0→1`, `1→0`, `0→2`, `2→0`, `0→3`, `3→0`, `0→4`, `4→0`）各有一个独立的掌握度状态。维度（5个）仅作为分组展示容器，本身不追踪掌握度。

### 4.2 向量掌握度 JSON 结构

每个向量方向各有以下字段：

```json
"0→1": {
  "label": "方名→症状",    // 向量语义标签（用于前端展示）
  "level": 0,              // 艾宾浩斯等级（0-5，见4.4节）
  "status": "未知",       // 掌握状态（见4.3节）
  "last_result": null,     // 上次答题结果（"right"/"wrong"/null）
  "last_review": null,     // 上次复习日期（ISO日期/null）
  "streak_right": 0,      // 当前等级下连续答对次数
  "streak_wrong": 0,      // 当前等级下连续答错次数
  "total_rights": 0,      // 累计答对次数（历史累计，不随等级重置）
  "total_wrongs": 0,      // 累计答错次数（历史累计，不随等级重置）
  "history": []           // 最近10次答题记录（可选，格式：[{"date":"2026-06-11","result":"right"}]）
}
```

### 4.3 掌握状态定义

| 状态名 | 含义 | 触发条件 |
|--------|------|---------|
| `未知` | 从未被抽中测试 | `last_result`为null且`last_review`为null |
| `从未掌握` | 被抽中过，但一次都没对 | 历史答题记录中无`"right"`，且答题次数≥1 |
| `正在学习` | 错→对但不稳定 | 最近一次对，但历史上有错，且`streak_right` < 3 |
| `已掌握` | 连续对3次，状态稳定 | `streak_right` ≥ 3，且`level` < 5 |
| `已遗忘` | 曾经掌握（`level`曾≥3），但现在答错导致`level`回退 | 本次答错且历史`level`曾≥3 |

**说明**：`level`（艾宾浩斯等级）和`status`（掌握状态）是两个独立标注。只看`level`会骗人——比如标着`level:4`（D+7），但上次做错了，`status`实际是`已遗忘`。

### 4.4 艾宾浩斯等级制度

**定位**：艾宾浩斯是后台机制，不是用户体验的主角。用户看到的主角是"技能树/能力树的可视化"。

**等级表**：

| 等级 | 时间点 | 说明 |
|------|--------|------|
| 0 | D（学习当天） | 初始/未知 |
| 1 | D+1 | 第1次复习完成 |
| 2 | D+2 | 第2次复习完成 |
| 3 | D+4 | 第3次复习完成 |
| 4 | D+7 | 第4次复习完成 |
| 5 | D+30 | 所有艾宾浩斯周期完成，进入待抽检堆 |

**说明**：等级（level）是时间进度（学了多久），不是能力进度（掌握了多少）。不显示百分比，只显示技能树可视化。

**卡片整体掌握度**：加权平均，核心向量权重更高。

**权重分配**：
- `1→0`（症状→方名）：权重 3（临床核心能力）
- `0→1`（方名→症状）：权重 2
- `0→2`（方名→药物）：权重 1.5
- `2→0`（药物→方名）：权重 1
- `0→3`（方名→用法）：权重 1
- `3→0`（用法→方名）：权重 0.5
- `0→4`（方名→病机）：权重 1
- `4→0`（病机→方名）：权重 0.5

**计算公式**：`整体掌握度 = Σ(向量掌握度 × 权重) / Σ(权重)`

**向量掌握度映射**（基于status，不是level）：
- `未知` = 0%
- `从未掌握` = 10%
- `正在学习` = 30-60%（根据 `streak_right` 线性插值）
- `已掌握` = 80%
- `已遗忘` = 20%

### 4.5 答题后状态变更规则

**答对**：

```python
if answer == "right":
    streak_right += 1
    streak_wrong = 0
    last_result = "right"
    last_review = today
    if streak_right >= 3:
        level = min(5, level + 1)   # 升级（最高5）
        streak_right = 0
        streak_wrong = 0
        if level == 5:
            status = "已掌握"
            # 移入待抽检堆
        else:
            schedule_next_review(level)  # 按新等级排下次复习时间
```

**答错**：

```python
elif answer == "wrong":
    streak_wrong += 1
    streak_right = 0
    last_result = "wrong"
    last_review = today
    if streak_wrong >= 2:
        level = max(0, level - 1)   # 降级（最低0）
        streak_right = 0
        streak_wrong = 0
        status = "已遗忘" if level < 3 else "正在学习"
        schedule_next_review(level)
    else:
        # 第一次答错：不降级，下次复习仍按当前等级排期
        schedule_next_review(level)
```

**关键规则**：
- 答错不升级，停留在当前等级
- 连续错2次才降级（不是立即降级）
- "连续对3次"是在**当次复习session内**连续答对，不要求跨天

### 4.5.1 Session结束条件

**定义**：Session是用户一次连续的学习/测试活动。

**Session开始**：用户打开某张卡片并开始学习/测试 → session开始

**Session结束**（满足任一条件即结束）：
1. 用户手动点击"结束学习"按钮
2. 系统检测到用户5分钟无交互（鼠标、键盘、触摸事件）
3. 用户切换卡片（离开当前卡片）

**关键说明**：
- Session结束后，"连续对3次"的计数（`streak_right`）清零，不跨session累计
- Session结束后，本次session的答题记录存入`history`数组

### 4.6 任务生成时机

任务由WorkBuddy在以下时机生成：

#### 4.6.1 每日凌晨任务生成

**触发**：每日凌晨（如03:00），WorkBuddy自动运行

**流程**：
```
1. 扫描所有卡片的所有向量
2. 找出 `next_review` ≤ 今天的向量 → 加入今日复习任务
3. 找出 `status` = "已遗忘" 的向量 → 加入今日复习任务（优先）
4. 生成今日学习任务清单 → 写入 `tasks/daily_YYYYMMDD.json`
5. 更新 `_sync_state.json` 的 `last_task_generate` 字段
```

**输出**：`tasks/daily_YYYYMMDD.json` 包含今日需要复习的卡片ID、向量、优先级

#### 4.6.2 用户主动学习时间

**触发**：用户在前端程序点击"开始学习"或完成快速筛选测试

**流程**：
```
1. 用户完成快速筛选测试（3-5题）
2. 答错的向量 → 加入今日学习列表（高优先级）
3. 答对的向量 → 如果连续在快速筛选中对≥2次，暂时移出今日学习列表
4. 生成今日学习路径 → 前端程序读取并展示
```

#### 4.6.3 随机测试（抽检）任务

**触发**：用户在前端程序点击"随机测试"或系统空闲时自动弹出

**流程**：见4.7节

### 4.7 随机测试（抽检）规则

随机测试是从"待随时抽检堆"随机抽取卡片/向量进行测试，目的是检验长期记忆。

#### 4.7.1 抽检出题规则

**抽取范围**：`status` = "已掌握" 且 `level` = 5 的向量（即已完成所有艾宾浩斯周期）

**抽取数量**：每次抽检抽取1-3个向量（可配置）

**出题方向**：随机抽取该向量的一个方向（如向量`1→0`，题目可能是"症状→方名"或"方名→症状"）

#### 4.7.2 答题后处理规则

**关键原则**：随机测试是"无预期测试"，不应惩罚用户。只记录结果，不改变学习进度。

**答对**：
```
last_result = "right"
last_review = today
# 不更新 level，不更新 streak_right，不升级
# 目的：记录"用户还记得"，但不提前进入下一个复习周期
```

**答错**：
```
last_result = "wrong"
last_review = today
# 不更新 level，不更新 streak_wrong，不降级
# 但标记为"需要关注"：将该向量从"待随时抽检堆"移回"待复习堆"
# 目的：让用户重新学习这个向量，但不惩罚（不降级）
```

**状态变更**：
- 答错后，`status` 从 "已掌握" 变为 "已遗忘"（但`level`不变）
- 该向量重新进入正常复习流程（从等待区重新开始艾宾浩斯周期）

#### 4.7.3 抽检频率控制

**自动抽检**：系统每天最多抽检1次（避免用户疲劳）

**手动抽检**：用户可主动点击"随机测试"进行抽检

### 4.8 向量分级追踪规则

8个训练向量分为**核心向量**和**次要向量**，采用不同的复习频率和抽检策略。

#### 4.8.1 向量分级定义

**核心向量**（临床核心能力，高频复习）：
- `1→0`（症状→方名）：权重 3，每天最多复习 2 次
- `0→1`（方名→症状）：权重 2，每天最多复习 1 次

**次要向量**（辅助能力，降低频率）：
- `0→2`（方名→药物）：权重 1.5，每 3 天最多复习 1 次
- `2→0`（药物→方名）：权重 1，每 5 天最多复习 1 次
- `0→3`（方名→用法）：权重 1，每 7 天最多复习 1 次
- `3→0`（用法→方名）：权重 0.5，每 7 天最多复习 1 次
- `0→4`（方名→病机）：权重 1，每 5 天最多复习 1 次
- `4→0`（病机→方名）：权重 0.5，每 7 天最多复习 1 次

#### 4.8.2 复习频率控制

**核心向量**：
- 每天可复习多次（上限见4.8.1）
- 艾宾浩斯周期正常进行（D+1, D+2, D+4, D+7, D+30）

**次要向量**：
- 降低复习频率，避免用户疲劳
- 艾宾浩斯周期延长：D+2, D+4, D+7, D+14, D+30（周期翻倍）
- 每天最多复习次数见4.8.1

#### 4.8.3 抽检频率控制

**核心向量**：抽检优先级高，每周抽检 2-3 次

**次要向量**：抽检优先级低，每 2 周抽检 1 次

```
               │
               ▼
┌─────────────────────────────────────────────┐
│         JSON文件层（真相源）                 │
│  - 卡片JSON（02-读书笔记/理论/）            │
│  - 经验卡片JSON（02-.../experiences/）      │
│  - 掌握度JSON（存在卡片JSON的mastery字段）   │
│  - 同步状态JSON（_sync_state.json）          │
└─────────────────────────────────────────────┘
```

### 6.2 职责边界详细说明

| 组件 | 能做 | 不能做 |
|------|------|-------|
| **前端程序** | 展示卡片、收集答题、调用AI API、将答题结果发送给WorkBuddy API | 不能自己计算掌握度、不能自己做晋级/降级决策、不能直接写JSON文件 |
| **WorkBuddy API** | 接收答题结果、计算掌握度、写入JSON、返回更新后的状态 | 不能参与实时对话（AI导师对话由用户前端调用用户自己的API完成） |
| **AI导师** | 接收用户输入+原文，进行battle分析，生成三级笔记 | 不能修改JSON文件（写入由前端程序完成，通过WorkBuddy API） |

**关键原则**：
1. 所有状态变更（掌握度、等级、next_review）必须由WorkBuddy API计算并写入JSON。前端只负责收集和展示。
2. 前端不能直接写JSON文件，必须通过WorkBuddy API。避免并发冲突和数据不一致。
3. WorkBuddy API是唯一的状态变更入口。
