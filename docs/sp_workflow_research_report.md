## 三、现有工作流 vs 理想工作流

### 3.1 现有工作流（实际执行路径）

```
用户指令 → AI 读取 SKILL.md → AI 读取 source_article_map.md（手动浏览）
  → AI 选择人格（凭经验）→ AI 从 oral_expression_guide.md 选取表达
  → AI 手工编写 JSON → 用户审核 → 保存到 sp_cases.json
```

**特点**: 
- 高度依赖 AI 的"阅读-理解-创作"能力
- 每次生成 1-3 个病例，无法批量
- 无自动化验证，依赖事后审计（如本次审计发现 formula_id 不匹配）
- 干扰项选择凭经验，无系统化的"从 35 方中筛选同病异方/同方加减"的算法

### 3.2 理想工作流（目标状态）

```
输入: 目标方剂列表（如"全部太阳病篇 16 方"）
  ↓
Step 1: 读取 source_article_map.json（机器可读）
  → 提取 symptom_pool、clue_map、difficulty、关联条文
  ↓
Step 2: 自动分配人格
  → 根据 chapter + difficulty + 症状特征，从 persona_system.md 选择 persona_id
  → 根据 verbosity 规则生成 word_count 范围
  ↓
Step 3: 自动构建 symptom_pool → 口语表达映射
  → 从 oral_expression_guide.md 索引每个症状的 L1/L2 表达
  → 根据 persona 的 L3 pool 随机选择噪声类型和文本
  ↓
Step 4: 自动生成干扰项
  → 从 35 方中按 distractor_type 策略筛选（同病异方/同方加减/相邻编号等）
  → 自动验证干扰项的 formula_id 存在于 formula_cards.json
  ↓
Step 5: 组装 JSON + 自动验证
  → 按 json_schema.md 组装完整 JSON
  → 自动验证：article_id 一致、formula_id 存在、字数范围、症状数范围
  ↓
Step 6: 输出到 sp_cases.json + 登记 CHANGELOG
```

### 3.3 差距分析

| 差距项 | 严重程度 | 现状 | 目标 | 解决方案 |
|---|---|---|---|---|
| source_article_map 非机器可读 | 🔴 高 | YAML-like Markdown | 结构化 JSON 或解析脚本 | 构建解析器或转换格式 |
| 无自动人格分配 | 🟡 中 | 凭经验手动选择 | 按 chapter + difficulty 自动映射 | 在 persona_system.md 中补充完整映射表 |
| 无批量生成能力 | 🔴 高 | 每次 1-3 例 | 一次生成 10-20 例 | 编写 Python 批量生成脚本 |
| 无自动干扰项选择 | 🟡 中 | 凭经验手动选择 | 从 35 方中按类型筛选 | 在 json_schema.md 中补充算法规范 |
| 无自动验证 | 🟡 中 | 事后审计 | 生成时自动校验 | 扩展 governance.py 或编写 SP 验证器 |
| 口语表达库无索引 | 🟡 中 | 凭经验手动选取 | 按 symptom 关键词自动索引 | 构建 symptom → 表达映射 JSON |
| 六经覆盖不均衡 | 🟡 中 | 太阳病 6 例，其余 2 例 | 每经至少 3 例 | 按优先级批量生成 |

## 五、下一步建议（用户决策）

### 方案 A：先补齐基础设施，再批量生成
- 先执行阶段一（2 天），构建自动化工具
- 再执行阶段二（2-3 天），批量生成 40 例
- **优点**: 生成质量高、可复现、后续维护成本低
- **缺点**: 需要额外投入 2 天基础设施，无法立即获得新病例

### 方案 B：直接批量生成，边做边优化
- 跳过阶段一的部分工作，直接用现有文档批量生成
- 生成 20 例（Batch 1-3 + 部分 Batch 4-5）
- **优点**: 快速获得可用病例，满足临床开方需求
- **缺点**: 生成质量依赖 AI 阅读记忆，可能出现本次审计发现的问题

### 方案 C：混合推进
- 先快速生成 15 例（Batch 1-3），满足即时需求
- 同时并行构建基础设施（source_article_map.json、生成器）
- 基础设施完成后，用工具批量生成剩余 25 例
- **优点**: 兼顾速度与质量，是最务实的选择
