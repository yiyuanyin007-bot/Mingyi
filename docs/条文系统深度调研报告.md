### 6.2 数据文件拆分策略（避免膨胀）

当前 `formula_cards.json` 已经膨胀（9,708行），内嵌了 teacher_notes、clinical_cases、source_annotations。这违反了「按需加载」原则。

**建议拆分**：

| 文件 | 内容 | 体积预估 | 加载时机 |
|---|---|---|---|
| `data/source_cards.json` | 基础条文（1条/方） | ~50KB | 页面启动时 |
| `data/source_cards_extended.json` | 扩展条文（多方条文） | ~200KB | 点击「展开更多条文」时 |
| `data/annotations.json` | 注家讲解（按条文编号索引） | ~300KB | 点击「条文讲解」时 |
| `data/experience_cards.json` | 临床医案（结构化） | ~500KB | mastery Level 4+ 时 |
| `data/symptom_index.json` | 症状→条文反向索引 | ~100KB | 生成测试题时 |

**加载模式**：`fetch('../data/xxx.json')` 按需加载，不一次性全部加载到内存。

### 6.3 清洗规则（自动化 + 人工复核）

```python
# 自动化清洗规则
rules = {
    "原文标准化": [
        "『』→「」",  # 书名号统一
        "（）→ ()",  # 括号统一（但保留条文编号括号）
        "逐漏→遂漏",  # 已知OCR错误替换
        "微嘴→微喘",
    ],
    "编号校验": [
        "小红书笔记编号 vs 宋本通行本编号",
        "冲突时标注：{article_number: '第23条（小红书）/ 第22条（宋本）'}",
    ],
    "症状对齐": [
        "source_cards.symptoms 必须是 formula_cards.symptom_profile 的子集",
        "新症状出现时通知方剂卡片维护者",
    ],
    "来源追溯": [
        "每条数据保留：extracted_from, extracted_at, original_file",
    ],
}
```

## 七、与方剂卡片的联动模式（红线：不修改方剂卡片设计）

### 7.1 数据联动（只读接口）

```
条文系统 ──→ 读取 formula_cards.json ──→ 获取 symptom_profile、herbs、pathology
    │                                          ↓
    │                              用于校验：source_cards.symptoms 是否一致
    │                                          ↓
    │                              用于生成：注解中的「条文辨析」与「类方鉴别」
    │
    └──→ 读取 experience_cards.json ──→ 获取 clinical_cases
                  ↓
         用于生成：「症状频率统计」→ 反哺 symptom_profile.common
```

**红线**：
- ❌ 不修改 `formula_cards.json` 的 schema
- ❌ 不修改 `formula_cards.json` 的 `mastery` 结构
- ❌ 不修改 `formula_cards.json` 的 `data.canonical` 内容
- ✅ 可以读取 `formula_cards` 的任何字段，用于生成条文系统的派生数据
- ✅ 可以生成新的独立 JSON 文件（如 `symptom_index.json`），供 `index.html` 使用

### 7.2 给方剂卡片下一步工作的意见

**意见1：一方多条文的 `source_text_ids` 扩展**

当前 `formula_cards.source_text_ids` 是单元素数组（如 `["gui-zhi-tang-src-001"]`）。建议扩展为：

```json
{
  "source_text_ids": ["gui-zhi-tang-src-001"],
  "source_text_ids_extended": [
    "gui-zhi-tang-src-012",
    "gui-zhi-tang-src-013",
    "gui-zhi-tang-src-053",
    "..."
  ]
}
```

- `source_text_ids` 保持现有（主条文，不修改）
- `source_text_ids_extended` 新增（扩展条文，由条文系统维护）
- 这个字段是**新增字段**，不影响现有代码

**意见2：`references` 字段的迁移建议**

当前 `references` 内嵌在 formula_cards 中，导致 JSON 膨胀。建议：

```json
{
  "references": {
    "teacher_notes": [],  // 清空，迁移到独立文件
    "clinical_cases": [],  // 清空，迁移到独立文件
    "source_annotations": [],  // 清空，迁移到独立文件
    "_migrated_to": "data/annotations.json"  // 迁移标记
  }
}
```

- 这是一个**长期建议**，不是立即执行
- 需要前端代码配合修改加载逻辑
- 可以分步执行：先建独立文件，再逐步迁移

**意见3：新增 `symptom_frequency` 字段**

```json
{
  "data": {
    "empirical_distribution": {
      "symptom_frequency": {
        "汗出": 0.95,
        "恶风": 0.90,
        "头痛": 0.75
      }
    }
  }
}
```

- 由条文系统从医案中提取统计，写入 `formula_cards`
- 这个字段已经存在（`empirical_distribution`），只是当前为空
- 填充这个字段不会影响任何现有代码

## 八、与SP（标准化病人）系统的联动设计

### 8.1 SP系统的依赖关系

SP系统需要：
1. **SP病例数据** → `data/sp_cases.json`（已存在）
2. **条文依据** → 用于验证SP病例的处方是否正确
3. **症状对照** → SP病人的症状应与条文原文一致

### 8.2 条文系统对SP系统的输出

| 输出内容 | 格式 | 用途 |
|---|---|---|
| 条文原文 | `source_cards.json` | SP病例的「条文依据」字段 |
| 症状谱 | `source_cards.symptoms` | SP病例的症状设计参考 |
| 方证对照 | `formula_card.data.canonical` | 验证学习者处方是否正确 |
| 医案参考 | `experience_cards.json` | SP病例的「参考答案」设计 |
| 症状频率 | `symptom_index.json` | SP病例的症状组合概率 |

### 8.3 SP系统对条文系统的反馈

```
SP问诊流程：
  学习者提问 → SP回答症状 → 学习者开方
         ↓
  条文系统提供：该方剂的「条文原文」+「症状谱」
         ↓
  SP系统验证：学习者处方是否与条文一致
         ↓
  反馈给条文系统：哪些症状被学习者遗漏/误判
         ↓
  条文系统优化：更新 symptom_profile，标记「易遗漏症状」
```

### 8.4 联动接口设计

```json
// 条文系统提供给SP系统的接口数据
{
  "sp_case_id": "sp-gui-zhi-tang-001",
  "related_article_numbers": ["第13条", "第12条", "第95条"],
  "required_symptoms": ["汗出", "恶风"],
  "common_symptoms": ["头痛", "发热", "脉浮缓"],
  "contraindications": ["无汗", "脉浮紧"],
  "source_text": "太阳病，头痛，发热，汗出，恶风，桂枝汤主之。",
  "annotations": {
    "刘渡舟": "本条论述太阳中风表虚证...",
    "胡希恕": "桂枝汤证是表虚，不是真正的中风..."
  }
}
```

## 十、总结

> **现状**：项目拥有丰富的原始资料（238条小红书笔记、81个黄煌医案、505KB倪海厦注文、3,202个CHM HTML），但当前只开发了冰山一角。35目标方中，桂枝汤和麻黄汤各有20+条相关条文未被接入，大量临床医案和注家讲解沉睡在原始文件中。
>
> **核心矛盾**：数据 abundance（ abundance = 丰富） vs. 集成 scarcity（scarcity = 稀缺）。有数据，但缺乏「从原始资料到结构化条文」的工业化工作流。
>
> **解决方案**：建立「挖掘→记录→清洗→呈现」的四阶段工作流，以条文编号为根键，将小红书笔记、黄煌医案、倪海厦注文、CHM资料统一纳入。同时保持与方剂卡片的松耦合（只读接口，不修改schema），与SP系统的正向输出（提供条文依据和症状谱）。
>
> **最终目标**：让每一条《伤寒论》条文都成为一个「活的知识节点」——连接原文、注家讲解、临床医案、SP模拟、测试训练，形成从「背诵」到「临床」的完整学习链路。
