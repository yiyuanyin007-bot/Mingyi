## 踩过的坑

_错误的判断、失败的尝试、不完善的流程——以及从中得到的教训_

- 2026-06-13：PowerShell 不支持 `&&` 连接命令，执行多步命令时用分号 `;` 或分行执行。
- 2026-06-13：Shell 输出中文字符可能乱码，但文件本身是 UTF-8 正常的，要以文件内容为准，不要被 Shell 显示误导。
- 2026-06-13：关键词规则容易误判。例如"无汗"同时出现在症状词库和禁忌关键词中，导致葛根汤条文被误标为 contraindication。后续需要给规则加优先级或否定词上下文判断。
- 2026-06-13：没有方名的句子（如用法段"以水七升……"）无法自动归属，需要依赖段落上下文继承方名。
- 2026-06-13：Markdown 源文本会严重污染输出。表格的 `|`、标题的 `#`、加粗的 `**`、列表的 `*` 都会被当成句子内容。预处理时必须剥离 Markdown 标记。
- 2026-06-13：AI 生成的现代解读文本（如"桂枝类方与脑科学.md"）含有大量元话语（"我将按……分组""至此已完成分析"），这些内容不是卡片事实，会被误判为 experience 或 contraindication。
- 2026-06-13：目录/清单类段落（如"1. 桂枝汤 2. 桂枝加葛根汤……"）会触发大量 formula_name，但这些是目录不是条文，需要识别并跳过。
- 2026-06-13：PDF（倪海厦人纪伤寒论）不能直接输入脚本，需要先提取文本。20MB 影印版 PDF 需要 OCR 或 pdftotext 预处理。
- 2026-06-13：用 PyMuPDF 检查 PDF 后发现：234 页，每页都是图片，无嵌入文字。属于扫描版/影印版 PDF，必须用 OCR。`ReadFile` 和 `ReadMediaFile` 都无法直接读取 PDF 页面。
- 2026-06-13：Tesseract OCR 安装包下载很慢（20MB 用了近 1 小时），但用 Python urllib 的断点续传最终成功。下次大文件下载应直接放后台，不阻塞主流程。
- 2026-06-13：所谓".txt"文件可能是 HTML（如 倪海夏-人纪- 伤寒论.txt 是 GB2312 编码的 HTML），不能直接当纯文本处理。必须先检测编码、去 HTML 标签。
- 2026-06-13：GB2312 文本在 PowerShell 中输出会乱码，但写入 UTF-8 文件后读取正常。处理中文古籍时应避免依赖 Shell 直接显示，多用"写文件 → 读文件"验证。
- 2026-06-13：电子书文本常有版式断行问题（一页内强制换行、页眉页脚、两栏排版残留）。清洗时必须先"合并人工换行"再"按语义分段"，否则会把半句话当成一个段落。
- 2026-06-13：条文编号（如"二：""四一：""三七一："）是非常好的分段锚点。在清洗阶段按条文编号拆分，能大幅提升后续提取的粒度。
- 2026-06-13：范围清单越大，误触发越多。68 个方名的范围清单会在 倪海厦伤寒论 中产生 1221 个条目，其中大量是正文里顺带提到方名。后续需要考虑"方名是否作为方剂卡主体"的判定，而不仅仅是出现即提取。
- 2026-06-13：识别规则目前把"没有方名的解释性段落"也标为 experience，target_card=unknown。这类内容应绑定到最近的前文方名，或单独作为经验卡候选。
- 2026-06-14：bat 文件中 `start` 命令的窗口标题若使用中文，在某些环境下会因编码解析错误导致命令被截断。窗口标题应使用 ASCII 字符，中文说明放注释里。
- 2026-06-14：`timeout /t` 在非交互式 Shell 中可能行为异常，但用户双击 bat 时正常。bat 的验证应以真实双击为准，不能只看 Shell 执行结果。

## 待验证的假设

_有初步迹象但尚未确认的想法，标记在此以供后续验证或推翻_

- 2026-06-13：按句号切分句子是否会导致信息失真？需要跑真实《伤寒论》原文验证。
- 2026-06-13：初版症状库和药物库覆盖度是否足够？跑一次完整原文后统计遗漏率。
- 2026-06-13：仅靠关键字识别病机、经验是否够用？还是需要引入更轻量的语义判断？
- 2026-06-13：Markdown + YAML 的原始文件格式是否方便用户逐条审阅？还是需要改成表格或 JSON Lines？
- 2026-06-13：直接从 AI 解读文本中提取卡片，产出质量是否足够？还是更适合从原始条文（如 PDF）中提取，把 AI 解读作为经验卡补充？
- 2026-06-13：范围清单是只给方名就够了，还是需要同时给症状/药物词库？
- 2026-06-13：OCR 后的古文（繁体/竖排/影印）识别难度远高于现代 Markdown。是否需要在 OCR 后加一个"古文清洗/繁简转换"步骤？
- 2026-06-13：倪海厦 PDF 扫描质量如何？OCR 准确率能否支撑卡片提取？需要先跑几页样本验证。
- 2026-06-13：.doc 文件（桂林古本伤寒杂病论.doc、伤寒论.doc）是否也能提取文本？需要用 python-docx 或 antiword 测试。
- 2026-06-13：《伤寒悬解》CHM 解压出约 600 个 HTML 文件，是否比 倪海厦 txt 更适合做方剂卡来源？需要抽样对比。
- 2026-06-13：范围清单是否需要按篇章动态生成？比如处理太阳病篇时只给太阳病方剂，减少误识别。
- 2026-06-13：源文本清洗后是否应该先生成"清洗报告"（总段落数、平均段落长度、识别到的方名分布）再进入提取？
- 2026-06-13（待验证·卡片结构）：`source_text` 是否应该改为 `source_text_ids` 数组，并独立出 `source_card` 条文卡？因为一个方剂可能对应多条原文，一条原文也可能涉及多个方。
- 2026-06-13（待验证·卡片结构）：症状字段是否应拆分为 `core_symptoms`（主症/鉴别症）和 `secondary_symptoms`（兼症/共性症），以提升"症状→方名"向量的出题质量。
- 2026-06-13（待验证·卡片结构）：方剂卡是否需要 `confusable_formulas`（易混方）字段，用于临床模式组卷。顶层设计说鉴别内容存 AI 对话笔记，但前端临床模式需要具体干扰项。
- 2026-06-13（待验证·卡片结构）：经验卡是否应在学习详情页有一个折叠展示入口，而不是只作为独立文件存在。
- 2026-06-13（待验证·卡片结构）：`mastery` 是运行时状态不应由 text-to-cards 提取，但提取产出的数据必须能自动生成 8 个向量的题目。这是 extraction 的验收标准。
- 2026-06-13（待验证·工作流）：text-to-cards 下一步优先级应为：更新 schema → 小范围（桂枝汤/麻黄汤/葛根汤）提取 → 生成 confusable_formulas → CHM 对比 → PDF OCR。
- 2026-06-13（待验证·工作流）：关联卡片（variants/confusable）是否可以先由规则半自动生成（如变体名匹配、症状 Jaccard 相似度），再人工审阅修正？

## 工作方法优化

_流程、工具、习惯层面的改进记录_

- 2026-06-13：写 Skill 前先读 `skill-creator` 规范，明确 `SKILL.md` + `references/` + `scripts/` 的结构，避免返工。
- 2026-06-13：AI Skill 先做"能跑通第一步"的最小版本，用真实文本跑一遍，根据产出迭代规则，而不是一次性把规则写满。
- 2026-06-13：中间产物采用 Markdown + YAML block 格式，方便人审阅，也方便机器后续解析。
- 2026-06-13：用真实用户文件（旧版经方学习系统）跑 skill，比用人工造的短文本更能暴露问题。测试文本应覆盖 Markdown、PDF、纯文本三种格式。
- 2026-06-13：做文本提取类 skill，"预处理"和"识别"应该解耦。先写一个 `clean_text.py` 把 Markdown/PDF 洗干净，再输入 `segment_text.py`。
- 2026-06-13：测试 skill 时应先用小样本（如 10-20 段）跑通，确认格式和规则 OK 后再跑全书，否则产出文件太大（73MB 原始提取文件）难以审阅。
- 2026-06-13：清洗脚本应该输出"清洗报告"：原始字符数、清洗后字符数、段落数、检测到的编码、去除的噪声类型。方便快速判断清洗质量。
- 2026-06-13：Tesseract 下载完成后，下一步是在项目目录里静默安装，并配置 pytesseract 指向本地 tesseract.exe。安装路径应写进 SKILL.md 作为标准配置。
- 2026-06-14：前端做「动态 fetch + 内联 fallback」可以同时兼容本地服务器模式和直接双击文件打开，避免 file:// 协议下的 CORS 问题。
- 2026-06-14：桌面版和手机版最好做成两个独立 HTML 文件，而不是一个响应式折中方案。两者的交互逻辑差异很大（键盘 vs 触摸、一屏看完 vs 单栏滑动、高信息密度 vs 大按钮），独立版本更容易针对各自场景优化。
- 2026-06-14：训练类应用的键盘快捷键能显著降低心流中断。考试视图用 `1/2/3/4` 选选项、`Enter` 进入下一题，学习视图用 `Enter` 开始测试/`Esc` 返回，比鼠标点击更符合高频操作习惯。
- 2026-06-14：「一屏不滚动」和「内容多」的矛盾，可以通过双栏布局 + 默认只展示核心字段来缓解。左栏放「原文/症状/药物」等事实区，右栏放「病机/禁忌/煎服法/经验」等解释区，展开/折叠作为补充。

## 外部评审记录

_与外部专家（DeepSeek）的 battle 总结，记录被挑战的点、纠偏过程和最终共识。_

### 2026-06-13：DeepSeek 对方剂思维训练系统的评审

**初始误判**：评审者一开始以"有一定基础的学习者"为隐含用户，批评系统"把方剂当静态知识对象""8 个向量全是配对题""三栏布局信息密度过高"，总体判断为"基本不可行"。

**语境纠正**：设计者明确用户是"小白"——不知道方名、药物、典型症状和匹配规则。基础映射训练是小白阶段必须跨过的前置条件。评审者收回"基本不可行"判断。

#### 达成的核心共识

1. **原方锚定**：以《伤寒论》原文为基准，药物组成+比例为准，不强制固定克数；变种方必须标注参照来源（原文/倪海厦/其他）。
2. **数据飞轮优先于初始数据量**：初期数据少没关系，关键是交互质量、无感采集、标签规范。
3. **经验提示三级分层**：
   - Level 0（小白）：只提示绝对禁忌和否定症
   - Level 1（已掌握基础）：提示高频加减法，附带条件
   - Level 2（熟练者）：开放全量数据
4. **疗效记录客观化**：每条经验必须区分 `subjective_effective` 和 `objective_change`；仅主观好转的记录为"低置信度经验"。
5. **方剂谱系追踪**：用药记录保留 `lineage` 字段，记录"基准方→加减路径"。

#### 设计原则更新

- **卡片结构双轨制**：同时维护 `canonical`（原文标准）和 `empirical_distribution`（经验分布）。
- **症状三分法**：用 `necessary` / `common` / `excluding` 代替 `core` / `secondary`。
- **训练向量精简**：
  - 基础必备：方名↔症状、方名↔药物
  - 辅助保留：方名→煎服法（权重降低）
  - 安全防护：禁忌识别（独立向量）
  - 进阶预留：症状→加减法、多症状→多方排序
- **前端极简**：学习单栏、测试双栏、统计独立页；去掉"逾期"标签和红黄绿焦虑色。
- **后台提取 MVP**：只做 `source_card`（条文卡）自动提取；`formula_card` 由学习过程逐步填充；`experience_card` 完全手工；OCR 扫描 PDF 不值得投入。
- **混淆管理个人化**：不静态存 `confusable_formulas`，改为每个用户维护个人"混淆矩阵"，训练时优先用个人高频混淆方作干扰项。

#### MVP 定义

保留：卡片管理（SRS）、AI 导师对话、条文卡自动提取。
删除：症状二分、静态 confusable、方名↔用法独立向量、三栏布局、复习红绿灯、经验卡自动提取、OCR。
形态：方剂索引表 + AI 辨证对话 + 三种卡片（条文卡、方剂索引卡、辨证过程卡）。

#### 待解决的关键问题

1. **方剂归属判定**：加减到什么程度仍算原方？MVP 不严格判定，但 `lineage` 字段必须预留。
2. **Level 0→1 升级标准**：建议以禁忌识别准确率 + 症状方名匹配率阈值作为条件。
3. **经验置信度权重**：主观有效 + 客观查体 vs 仅主观有效，MVP 阶段预设权重比 1:0.3。
4. **无感数据采集交互设计**：需与真实临床医生共同迭代，不在设计阶段完全确定。
